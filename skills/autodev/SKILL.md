# Autodev — 自動開発オーケストレーター（共通ワークフロー）

ハーネス（CC / Codex）共通のワークフロー正本。
エージェントの起動方法、人間との対話手段、マージポリシーなどのハーネス固有の動作は
呼び出し元のハーネス固有設定に従う。
- CC: `~/.claude/commands/autodev.md`
- Codex: `~/.codex/skills/autodev/SKILL.md`

## 絶対ルール

1. レビューは実装者とは別の新しいエージェントで行う。同一コンテキストの自己レビューを独立レビューとして扱わない。
2. 書き込みエージェントは同時に1つだけ動かす。複数の実装エージェントを同じ worktree で並列実行しない。
3. 読み取り専用で相互独立な調査だけ、必要に応じて並列化してよい。
4. ユーザーや他エージェントの既存変更を戻さない。依頼外のリファクタ・整形・依存更新・生成物更新を追加しない。
5. 子エージェントから孫エージェントを起動させない。親から直接起動する。
6. 実行していない検証を「通過」と報告しない。
7. 対象コードにメタコメント（「デモ用」「削除予定」等の作業メモ）を入れない。

## エージェント起動の共通規律

- 各エージェントには、目的・対象・制約・期待出力・必要なファイルまたは diff 範囲だけを渡す。
- 親の長い会話履歴をそのまま渡さない。
- 新しいレビューラウンドでは新しいレビューエージェントを起動し、前回のレビューエージェントを再利用しない。
- エージェント名を表示ラベルや task_name に書くだけで済ませず、利用可能なエージェント種別の指定で名前付きエージェントを選ぶ。
- 親は全エージェントの結果を待ち、矛盾を整理してから次の工程へ進む。

## 重大度と合格ライン

- **P0**: 致命的。セキュリティ事故、データ破壊、テナント漏洩、確実な重大障害。
- **P1**: 重大。主要機能破壊、認可バイパス、深刻なリグレッション、重大なデータ不整合。
- **P2**: 中程度。重要なバグ、要件漏れ、重要な境界条件の失敗、必要な検証不足。
- **P3**: 軽微。任意対応の改善、明確化、保守性、非ブロッカー。
- **合格 = 全レビューアで P0〜P2 ゼロ**。P3 は任意（ついでに直してよいが、P3 のために再レビューを回さない）。
- VERDICT とタグが矛盾する場合は**タグ（P0〜P2 の有無）を正**とする。

## Phase 1 — 難易度判定・実装者解決

タスクを理解し、light / full を判定する:
- **light**: 局所的、明確、低リスク、可逆。原則1ファイル、または同一責務のごく小さな変更。
- **full**: 複数ファイル / モジュール横断 / 要件不明瞭 / 認証・認可 / 個人情報 / 課金 / schema・migration / 不可逆変更。
- 判断に迷う場合は full。ユーザーが `light` / `full` を指定していればそれに従う。
- 判断に迷う・要件が曖昧なら【ハーネス固有】方法で人間に確認。
- 実装者の解決:【ハーネス固有】既定実装者と切替条件はハーネス側で定義。

## Phase 2 — コードベース調査

full では原則必須。light でも対象箇所や影響範囲が不明なら実施する。
-【ハーネス固有】調査エージェントの起動方法はハーネス側で定義。
- 結果を統合し、確認済み事実 / 推論 / 未確認事項を分離する。
- 独立した論点が複数ある場合だけ、複数の調査エージェントを並列起動してよい。
- 調査結果だけで設計を確定できない場合は追加調査を1回。価値が薄い広範スキャンは続けない。

## Phase 3 — 計画作成（full のみ）

計画を `tasks/autodev/<slug>.md` に作成。内容:
- 目的 / 非技術者向け要約 / 現状と根拠 / 設計とトレードオフ
- 対象ファイル・対象モジュール / 実装手順
- **テスト方針**: 何を保証するテストを足すか。足さないならその理由を1行。
  テスト方針正本（プロジェクトの `tests/README.md` 等があればそちら優先、無ければ
  `~/.agents/docs/test-policy.md`）に従う。ガードを足す計画なら、**それを壊したら
  落ちるはずの変異**を計画に列挙する（原則6。列挙しない変異は守られないのが実測）。
- **完了条件**: 第三者が機械的に判定できる形（×「正しく動く」→ ○「コマンドXの出力がY」）。
- やらないこと / リスクと戻し方 / ユーザー判断が必要な項目
- プロジェクトの CLAUDE.md / AGENTS.md の規約を念頭に置く。
- **設計判断（方向性・トレードオフ・技術選択）は勝手に決めない**。【ハーネス固有】人間への確認方法はハーネス側。

## Phase 4 — 計画二重レビュー（full のみ・合格までループ）

修正はオーケストレーター（autodev）が一元管理。各レビューアは1回レビューして指摘を返すだけ。

1. **レビュー（各レビューア1回ずつ）**:【ハーネス固有】レビューエージェントの起動方法はハーネス側。初回は完全ゼロベース。
2. **集約・判定**: 全レビューアの指摘を集約（重複は1件に）。全レビューアで P0〜P2 ゼロ → Phase 5 へ。
3. **修正（autodev が一元）**: 残る P0/P1/P2 に沿って autodev が計画を修正。設計判断が絡めば人間に確認。
4. **再レビュー（各レビューア1回ずつ）**: 再レビューは「①前回指摘への対処確認 + ②修正起因の新規問題」の2軸で独立に評価。→ 2 に戻る。
- **上限: 3ラウンドで未収束** →【ハーネス固有】上限到達時の処理はハーネス側（エスカレーション / 残指摘整理して進行）。

## Phase 5 — 実装前ゲート

【ハーネス固有】人間承認の要否と方法はハーネス側で定義。
- 未解決の製品判断、セキュリティ判断、データ判断が残る場合は自動実装しない。

## Phase 6 — 実装

共通: 計画の対象ファイルに閉じる。実装中の設計判断は人間に確認する（計画で決めていない方向を勝手に決めない）。
ビルドゲート（typecheck / lint / test / build 等、プロジェクト固有値から解決）が green になるまで直す。

【ハーネス固有】実装エージェントの起動方法、cross-tool bridge の呼び出し規律はハーネス側。

### エスカレーション受け口（共通）
実装エージェントが `NEED-DECISION: <質問>` を返したら:
1. **一次トリアージ**: 計画・既存決定・プロジェクト規約から答えられる質問は autodev が自答。
2. **真の設計判断**だけ人間へ。背景と選択肢を提示してから確認する。
3. **回答を差し戻して続行**。【ハーネス固有】差し戻し方法はハーネス側。
4. **下した決定は計画文書の「実装中の決定」節に追記**（判断の経緯がレビューと履歴に残る）。
- `NEED-DECISION` が頻発する場合は計画の曖昧さが根因——Phase 3/4 に戻る判断をする。
- **同じブロッカーで2回止まったら推測で続けず停止する。**

### フォールバック（共通）
usage limit / 実装未完走 / 差し戻し2ラウンドで進展なし →【ハーネス固有】フォールバック先と方針はハーネス側。

## Phase 7 — 検証

実装エージェントの報告だけで完了扱いにしない。親が現在の worktree で検証を再実行する。
1. 変更ファイルと `git status` を確認。依頼外の変更がないか確認。
2. プロジェクトの検証ゲートを対象に近い順で実行（テスト → lint → typecheck → build → migration検証 → E2E）。
3. プロジェクト指示に必須ゲートがあれば実行する。
4. 失敗した場合は、今回の変更起因か既存失敗かを分ける。
5. 実行不能なゲートは理由と未検証リスクを明記。未実行を pass にしない。

## Phase 8 — 差分二重レビュー（合格までループ）

コード変更がある場合、light / full を問わず必須。構造は Phase 4 と同じ。

### レビュー対象
- commit 済み: `<base-ref>...HEAD`
- 未 commit: staged + unstaged + 新規 untracked ファイルも対象にする。
- `origin/main...HEAD` だけを見て未コミット差分を落としてはいけない。

### ループ
1. **レビュー（各レビューア1回ずつ）**:【ハーネス固有】起動方法はハーネス側。初回ゼロベース。
2. **集約・判定**: 全レビューアで P0〜P2 ゼロ → Phase 9 へ。
3. **修正（autodev が一元）**: 修正後は**ビルドゲート green 確認 → commit & push**（push しないとレビュー済みコードと PR が乖離する）。
4. **再レビュー（各レビューア1回ずつ）**: 2軸評価。→ 2 に戻る。
- **上限: 3ラウンドで未収束 → エスカレーション**（次がマージのため）。

## Phase 9 — PR 作成

【ハーネス固有】PR 作成の条件（自動 or ユーザー明示）はハーネス側。
- 独立差分レビューとローカル検証が収束してから commit する。
- commit 前に `git status` と対象差分を再確認。秘密情報・不要な生成物・依頼外ファイルが含まれていないか確認。
- ブランチ規則: タスク用 feature ブランチに既にいればそれを使う。長寿命ブランチ（`claude/xxx` 等）や main 系にいる場合は、fetch 後に origin/main からタスク用 feature ブランチを新設（ローカル main は stale の可能性）。
- commit メッセージ・branch 命名・PR テンプレートはプロジェクト規約に従う。
-【ハーネス固有】計画文書の commit 可否、PR タイトル・本文の言語はハーネス側。

## Phase 10 — CI・マージ

- CI 確認（`gh pr checks` 等）。長時間終わらない場合（目安15分超）は人間に報告。
- **CI fail 時の戻り先**: 自変更起因で直せる場合は修正→ビルドゲート→commit&push。ロジック変更を伴うなら **Phase 8 に戻る**。軽微（lint・フォーマット・フレーク再実行）なら Phase 10 を再確認。直せない場合はエスカレーション。
- ビルドゲート/CI の失敗が自分の変更と無関係（ベースで既に落ちている）場合は、勝手に直さずスコープ逸脱として人間に報告。
- **未 push・未コミットの変更が無いこと（`git status` clean）を確認**。未追跡ファイルも対象——計画文書が未追跡で残っていたら commit 漏れの可能性を確認。
-【ハーネス固有】マージの条件・方法はハーネス側。

## Phase 11 — worktree/branch closeout

マージ（Phase 10）が完了したら、その場で後片付けする。手順の正本は `git-ops` スキル（§2.5 / §3）。
- このタスクが作った一時 worktree と、マージ済みの作業ブランチを closeout する（worktree削除→ブランチ削除→prune）。**マージだけで終わらせない。**
- **未処理の worktree/ブランチを残したまま「完了」と報告しない。**
- ロック等で削除不能なら、保持理由と次の削除条件を最終報告に明記する（放置＝完了と扱わない）。
-【ハーネス固有】リモート/ネットを要する片付け（`git push origin --delete`・`gh` 照合・棚卸しの `--remote`）の可否は git-ops §1.5 と各ハーネスのラッパーに従う（例: Codex はサンドボックスでローカルのみ）。

## 停止条件（集約）

次の場合は自動継続しない:
- 重要仕様が一意に定まらない。
- 公開API、認可、データ形状、migration、不可逆操作の判断が必要。
- 依頼範囲外の大きな変更が必要。
- 既存の未コミット変更と衝突する。
- 独立レビューエージェントを起動できない。
- 同じ実装ブロッカーが2回続く。
- 3レビューラウンドで P0〜P2 が収束しない（Phase 8）。
- 必須検証が実行不能で未検証リスクが高い。
- 不可逆操作（本番データ削除・破壊的SQL・秘密情報の外部送信）は実行前に人間確認。
-【ハーネス固有】追加の停止条件はハーネス側。

## 最終報告

次を含める:
- 難易度判定: light / full
- 実装者（フォールバック有無も）
- 計画ファイルと計画レビュー結果（ラウンド数、各レビューアの判定）
- 変更ファイルと変更内容
- 実行した検証コマンドと結果
- 差分レビュー対象・ラウンド数・各レビューアの判定
- PR 番号 / CI 結果 / マージ結果
- worktree/branch closeout（Phase 11）: 片付け済み / 残存があれば「保持理由＋次の削除条件」
- 未検証事項、残存リスク、ユーザー判断事項
- コード変更があるのに独立差分レビューを完了できなかった場合「完了」「レビューpass」と表現しない。
-【ハーネス固有】追加の報告項目はハーネス側。
