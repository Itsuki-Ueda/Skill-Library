# verify-ops — プロジェクトの検証スキルを作る・点検する

アプリを起動し、人が使うのと同じ道筋で操作し、証拠を残す手順を、プロジェクトごとに1つの
スキル（以下「verify」）にまとめる。verify を読めば、初めてそのアプリを触るエージェントでも、
タスクの途中で同じ手順を流せる状態にする。

agent-team には依存しない。agent-team・autodev・通常のセッションは、verify があれば読んで使う側。

## 置き場所と公開範囲

| もの | 置き場所 | 公開 |
| --- | --- | --- |
| このスキル（作り方・点検の仕方） | `~/.agents/skills/verify-ops/` | 公開リポジトリ。一般的な書き方だけ |
| verify（そのアプリ専用の手順） | プロジェクトのリポジトリの `.agents/skills/verify/` | そのリポジトリと同じ |

- アプリ名・URL・テストアカウント・DB の接続先・業務の固有名詞は verify 側にだけ書く。このスキルには書かない。
- verify は契約やプロンプトからパスで渡して読ませる。Claude Code に自動で見つけさせたい場合だけ、
  リポジトリの `.claude/skills/verify` から `.agents/skills/verify` へリンクを張る。
- verify の commit・push はそのリポジトリの運用（git-ops）に従う。

## 証拠の決まり（verify にそのまま書き写す）

1. **人が通る道筋で操作する。** 内部の値を直接書き換える、テスト専用の入口を使う、は証拠に数えない。
   部品を単体で組み立てて確かめる方式を使う場合は、その方式で通らない道筋を verify に明記する。
2. **操作と、その結果の状態の両方を残す。** 最後の画面だけでは足りない。
3. **見た目に加えて副作用を確かめる。** 書き込まれたファイル・DB の行・送られたもの。画面に正しい値が出ても、保存された値が違うことがある。
4. **偽物は、本番でも外部と切り離されている境界だけ。** ログインを通すための応答の差し替えは確認用のスクリプトの中だけで行い、
   アプリ本体に開発専用のログイン口や偽の API を組み込まない（本番に紛れ込む）。
5. **試し実行（dry-run・テストモード）は名前を信じない。** 実際に何を飛ばしているかを、ファイル・通信・git の変化で確かめる。
6. **通らないときは手順を弱めない。** 前提が揃わない機能は「失敗」と理由を報告し、理由を機能地図の「注意」に書く。
7. **本番のデータ・秘密の値・人の画面には触れない。** 既定は人の画面に出さない方式（画面外の描画・ヘッドレスのブラウザ）。
   画面に出す必要がある確認は、人間の許可を得てその旨を verify に書いた場合だけ。

## 作る

### 1. リポジトリを調べる（人に聞くのは、コードから分からないことだけ）

- **面**: 人が触るもの（Web 画面 / デスクトップの窓 / CLI / API）。複数あれば主なものを選び、残りを書いておく。
- **起動**: README・package の scripts・既存の起動スクリプト。ポート・環境変数・テストデータ・ログイン。
- **操作**: 既存の仕組みを先に使う（E2E のテスト、確認用スクリプト、HTTP で叩ける口）。無い場合だけ汎用の方法
  （Web はヘッドレスのブラウザ、CLI は疑似端末、API は HTTP）。
- **観察**: 取れる証拠（画像・応答の本文・ログ・終了コード・DB の状態）。
- **分離**: 2つ同時に起動できるか（ポート・データの置き場・プロフィール）。できないなら verify にそう書き、二重に動かさない。
- **実行場所**: 次の3つのどこで流せるか。CLI worker の sandbox の制限は `~/.agents/docs/codex-protocol.md` §3(e)(f) を見る。
  - CLI worker の sandbox の中（例: Linux では開発サーバーの待ち受けに `cx-run.sh --net` が要る）
  - 進行役（親・executor）が sandbox の外で
  - 人間だけ（秘密の値・本番・外部サービスのデータが要るもの）

checkout がそのままでは起動しない場合は、先に直すか、何が足りないかを正確に報告する。壊れた状態で書いた手順は誤りを教える。

### 2. verify を書く

`references/verify-template.md` の形で `.agents/skills/verify/SKILL.md` を書く。各節は調べた事実で埋め、`{}` を残さない。

- **起動**: 確認用に起動するコマンドと、「使える状態になった」の見分け方（プロセスが応答した、ではなく使える状態）。空のデータから使える状態まで。止め方も。
- **健康診断**: 「このインスタンスを操作してよいか」を読むだけで答える1回の確認（起動している・正しいビルド・ポートが自分のもの・ログインが有効）。様子がおかしいときは最初にこれを流す。
- **操作**: このリポジトリの実際のセレクタ・コマンドで書く。座標や Tab の順番より、ラベル・data 属性・プロンプトの文字列・ルートのパスを使う。
- **証拠**: 何をどこに残すか。上の「証拠の決まり」を書き写す。
- **片付け**: 自分が起動したものだけを止める（プロセス名で止めない）。証拠は消さない。
- **実行場所**: 機能・手順ごとに、上の3つのどこで流せるか。
- **補助のスクリプト**: 実行できる状態にし、呼び方を本文に書く。

### 3. 機能地図を作る

`.agents/skills/verify/features/README.md`（目次）と、機能ごとに1ファイルを `references/feature-template.md` の形で作る。
最初は主な機能 3〜5 個でよい。既存の確認スクリプトがある機能は、新しく書かずにそれを指す。
地図に入口が複数ある機能は、1つの入口だけ確かめて完了にしない。

### 4. 1つの機能で実証してから渡す

verify の手順だけを見て、起動 → 健康診断 → 1機能の操作 → 証拠 → 片付けを最後まで流す。
片付けの後に証拠が残っているかを確かめる。失敗したら直し、失敗した回にも片付けを流す。
**一度も流していない verify は下書きであり、渡さない。** 代わりの環境で実証した場合は、本番の実行場所では行われない手順を列挙し、未確認として残す。

### 5. つなぐ

- プロジェクトの `AGENTS.md` に1行: 「アプリの動作確認は `.agents/skills/verify/SKILL.md` に従う」。
- 実証の結果（流した機能・証拠の場所・未確認の手順）を人間に報告する。

## ログインのある Web アプリ

確かめる場所を3段に分け、毎回流すのは①だけにする。どれを使うかとログインの通し方は verify の「起動」「健康診断」に1回だけ書く。

| 段 | 場所 | ログイン | 確かめること |
| --- | --- | --- | --- |
| ① 手元 | 開発サーバー・本番ビルドを手元かクラウドのセッションで起動 | 確認用スクリプトの中の応答の差し替え、または `.env.local` 等の確認用アカウント | 画面・操作のほぼ全部。開発モードと本番ビルドで挙動が違う機能は本番ビルドで |
| ② 本物のデータ | 手元。DB は検証用の分岐・スキーマへ | 人が一度ログインし、ログイン状態を保存したファイルを使い回す | 保存・読み出し |
| ③ デプロイ先の preview | ホスティング側 | ホスティングの自動化用の通行証、または専用の CLI | デプロイでしか起きない差（環境変数・ビルド・リダイレクト）。マージ前に1回 |

- テスト用アカウントの最初のログイン、通行証の発行と環境変数への登録は人間が行う。エージェントは秘密の値を入力しない。
- 健康診断は、詰まった原因を名指しする（ログイン状態のファイルの期限切れ、通行証が未設定、DB に届かない、など）。

## デスクトップアプリ

- 既定は人の画面に出さない方式（画面外の窓・アプリ自身の描画で画像を作る）。入力の注入や画面の読み取りはしない。
- 本物の前面・入力でしか確かめられないものは、少数を1つのスクリプトに集め、実行場所を「進行役が sandbox の外で」とする（sandbox の中では前面を取れない）。
- 確認用のプログラムは、失敗を例外で落とさず終了コードで返す（落ちるとエラーの窓が人の画面に出る）。

## 点検する

アプリが変わると機能地図は古くなる。区切りのよいとき（大きなミッションの後など）に流す。

1. **対象を見つける**: `.agents/skills/verify/`。無ければ点検せず「作る」を案内する。
2. **目次の整理**: 目次と機能ファイルの過不足・重複・切れたリンクを直す。
3. **ソースを読む**: 機能ファイル1つにつき読み取り専用の調査担当を1つ、同時に起動する。各担当は「この機能はどう動くか」をソースから説明し、地図とのずれを根拠付きで挙げ、確かめ方を1つ返す。アプリは動かさない。
4. **突き合わせ**: ずれの指摘を抜き取りで確かめる。最近の変更で地図に無い機能があれば、ソースのパスを根拠に足す。
5. **全部の機能を実際に流す**（ソースがきれいでも省かない）。操作は進行役が1つずつ行う。最初と、失敗の後には健康診断を流す。証拠は最後まで残す。前提が揃わず届かない機能は、足りない前提と試した道筋を書く。
6. **仕分け**: 説明の誤り → 地図を直す。動くのに手順で操作できない → 手順を直して流し直す。アプリが本当に壊れている → 人間に報告し、地図で取り繕わない。
7. **結果**: 次のどれかを言う。
   - 問題なし
   - 直した（verify のディレクトリだけを直す。プロダクトのコードは触らない）
   - 止まった（何が止めたかを書く）
