# /autodev — CC ハーネス固有設定

**正本ワークフロー `~/.agents/skills/autodev/SKILL.md` を最初に読み、全フェーズに従うこと。**
このファイルは CC 固有の動作のみを定義する。正本側の【ハーネス固有】を以下で埋める。

## 前提
- `~/.agents/docs/codex-protocol.md` を Read（Codex 呼び出し規則の正本）。
- プロジェクト固有値（ビルドゲートコマンド・gh 認証切替など）は CLAUDE.md・メモリ・package.json から解決。
- **レビュー粒度は CC・Codex で対称**（各ラウンド 1 回レビューして指摘を返すだけ）。修正は autodev が一元管理。
  autodev 内では `/cxplan`・`/cxloop` の自己完結ループは使わない（単体使用時のみ自己完結）。
- **CC レビューは `reviewer` エージェント定義**（`~/.agents/agents/reviewer.md`、model: opus・読み取り専用。
  VERDICT 形式・P0〜P3 タグ・証拠必須・除外規則・再レビュー2軸は定義側が正本——呼び出し時はモードと対象だけ渡す）。
  定義が使えない場合は `Agent`(general-purpose, model: opus) に同等規律をプロンプト先頭に付与して代替。
- ☑ この工程の確認: codex-protocol.md を Read した / プロジェクト固有値を解決した / git・gh 前提を満たす。

## 実装者の解決
引数に `codex` があれば実装者 = Codex、無ければ実装者 = CC（既定）。

## 人間との対話
- 設計判断 → `AskUserQuestion`（先にチャットへ判断の背景と選択肢を**プログラミングが分からない人にも伝わる平易な日本語**で書いてから聞く）。
- Phase 5（人間承認）→ チャットにプラン要約を書き `AskUserQuestion` で承認。
  要約: 「このタスクで何がどう変わるか」を数行。
  設計判断は「**現在の予定**: ◯◯ ／ **他の選択肢**: △△」形式で、各選択肢にメリット・デメリットを1〜2個ずつ平易に添える。
  レビューの残指摘があればそれも平易に添える。
  選択肢: 承認 / 設計判断を変更したい / その他の修正要望。
- 承認 → Phase 6 へ。変更・修正要望 → 反映して Phase 4 ループに戻り、再合格後に再提示。

## light パスの省略
**軽量パスは人間ゲートゼロで自動マージまで行く**（完全自動方針の意図的な設計）。
計画・人間承認を飛ばして Phase 6（実装）へ直行。

## エージェント起動

### 調査
グローバル CLAUDE.md のオーケストレーション・プロトコル第1層に従い、researcher エージェントに委譲。

### レビュー（プラン: Phase 4 / 差分: Phase 8）
- **CC**: **新しい** `reviewer` にモードと対象だけを渡す。
  - プランレビュー初回: モード=プランレビュー＋plan file の絶対パスのみ（ゼロベース）。
  - プラン再レビュー: モード=プラン再レビュー＋修正後プランのパス＋前回指摘リスト＋修正サマリ（2軸は定義側）。
  - 差分レビュー初回: モード=差分レビュー＋diff 範囲 `origin/main...HEAD`（ゼロベース）。
  - 差分再レビュー: モード=差分再レビュー＋diff 範囲＋前回指摘＋修正サマリ。
- **Codex**: codex-protocol.md の**文書レビュー形＋雛形 8a**（初回 effort＝§1）。再レビューは **resume 形＋雛形 8b**（effort=high）。session id を記録、指摘は `-o` から読む。

### plan-probe（Phase 4 初回ラウンドのみ・両レビューと並走）
`plan-probe` エージェント（haiku 固定の測定器）に plan file のパスだけを渡す。
返ってきた言い換え（変更対象／やらないこと／完了条件の判定手順化／迷った箇所）をプラン原文と突き合わせ、
**ズレ＝曖昧箇所**として修正に流す。合否には数えない。プランを大幅に書き直したラウンドでは再実行してよい。

### 実装（CC 既定）
**グローバル CLAUDE.md のオーケストレーション・プロトコルに従う**
（Fable → Opus サブエージェントに委譲、Opus → 自分で実装）。

### 実装（Codex 指定時）
codex-protocol.md の**実装形（3d）＋雛形 8c ＋規律 §13**。仕様 = プラン文書全文（軽量パスはタスク内容＋対象ファイル＋完了条件）。
- **分担（実測済みの物理制約）**: Codex はコードを書くだけ。環境準備（`node_modules` 等）・ビルドゲート・commit・push・PR は全て autodev。
  委譲前に worktree でビルドゲートが実行可能なこと（依存インストール済み）を確認する。
- ビルドゲート red → 実装セッションへ resume で差し戻し。

## NEED-DECISION の差し戻し
- CC 実装者 → **SendMessage で同一エージェントへ**（新規 Agent を立てない＝文脈保持）。
- Codex 実装者 → **resume**（codex-protocol.md 3d の sandbox 指定込み）。

## フォールバック
Codex 実装時: usage limit / 実装未完走 / 差し戻し 2 ラウンド進展なし → **CC 実装に切り替えて続行**し最終報告に明記（パイプラインを止めない）。

## 計画レビュー上限到達時
残指摘を整理して Phase 5 へ進む（直後に人間承認があるため。Phase 8 と非対称なのは意図的——Phase 8 の次は自動マージのためエスカレーション）。

## PR 作成
- `tasks/autodev/<slug>.md`（計画文書）も PR のコミットに含める（レビュー文脈・設計判断の履歴をリポジトリに残す）。
- commit メッセージ英語＋末尾に `Co-Authored-By: Claude ...`。**PR のタイトル・本文は日本語**。
- gh 操作前にプロジェクト規約の認証切替を実行。

## マージ
gh 認証切替を再実行 → `gh pr merge --squash`。
マージ後のローカル後片付けはプロジェクト運用に従う（既定は何もしなくてよい）。

## 最終報告（CC 固有追加項目）
- 実装者（CC/Codex。Codex 時は実装 session id とフォールバック有無も）。
- プランレビュー: ラウンド数・CC 各ラウンド VERDICT・Codex session id。
- PRレビュー: 同様。

## ☑ 各工程の確認チェックリスト
正本ワークフローの各 Phase 完了時に以下を確認:
- Phase 1: 判定結果と理由を1行で報告 / 実装者報告 / 曖昧なら AskUserQuestion 済み。
- Phase 3: plan file 作成 / 設計判断は AskUserQuestion で確認済み。
- Phase 4: 両者 P0〜P2 ゼロ（or 上限到達で残指摘整理済み）/ 初回ラウンドで plan-probe 済み / Codex session id 保持。
- Phase 5: チャットにプラン要約書いた / AskUserQuestion で承認。
- Phase 6: 対象ファイルに閉じている / 設計判断確認済み / NEED-DECISION は受け口で処理しプランに追記 / ビルドゲート green。
- Phase 9: ブランチ規則どおり / プラン文書含めた / 認証切替済み / push 済み / PR 作成。
- Phase 8: 両者 P0〜P2 ゼロ / 修正後は毎回 push 済み / Codex session id 保持。
- Phase 10: ビルドゲート green / CI green（or 未設定）/ git status clean / 認証切替済み / マージ完了。
