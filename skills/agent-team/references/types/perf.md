# 作業の型: 性能

[1] で、依頼が遅い・重い・メモリが多いといった性能の改善ならこの型を使う。直すたびに測る。コードを読むだけで済ませない。
主に使う原則: 数字の出どころを説明する、本物で確かめる、小さく確かめながら積む。

## [2] 調査の問い

1. 基準の数字はいくつか。どの入口・データの大きさ・同時数で測ったか。測る前に、出したい主張を文で書いておく（例: 「6万行の書き出しが中央値で30%速くなる」）。
2. 上限を決めているものは何か（CPU、ロック、ディスク、ネットワーク、負荷をかける側）。プロファイルで名指しする。プロファイラは処理を遅くするので、報告する計測とは別の回で取る。
3. 安い順に、次のどれで目標に届くか。届いたら止める。
   1. やらない（結果を誰も使わない処理を止める）
   2. やるが、2回やらない（キャッシュ・再利用）
   3. 量を減らす
   4. 後でやる
   5. 気づかれないときにやる
   6. 並行してやる
   7. 安くやる

## [3] 契約の既定欄

- Acceptance に、目標の数字と、測る入口・データの大きさ・回数を書く。
- 1つ試すごとに測る。効かなかった変更は戻す。

## [6] 検証（数字を報告する前の7問）

答えはコードからの推測でなく、実行の証拠で書く。ざっくりの見積もりを頼まれただけなら1回でよいが、4と7は確かめ、1回だけだと書く。

1. なぜ2倍ではないか。上限を決めているものを名指しする。変更で数字が動かなかったなら、上限がその理由を説明する。
2. 両方を本番と同じ条件で動かしたか（リリースビルド、本番の設定、同じバージョンとデータ）。片方だけ既定の設定なら、比べたのは設定の違い。
3. 限界を超えていないか。帯域・コア数・変えた部分にもともとかかっていた時間と比べる。全体の10%の部分を消しても、速くなるのは最大で約11%。超えていたら、別のもの（キャッシュ、何もしていない処理、不具合）を測っている。
4. エラーを数えたか。失敗や成功以外の応答を数え、出力が正しいかも確かめる。拒否は速く、タイムアウトと再試行は遅い。
5. 再現するか。それぞれ5回以上、交互に（A, B, A, B と）流し、中央値と範囲を書く。差が回ごとのばらつきより小さければ、差は無い。
6. 全体で効くか。部分の速さの横に、利用者が待つ入口から出口までの時間を測り、部分の割合を書く。
7. 本当に処理が走ったか。計った区間の中で、要求が届いた、行が書かれた、結果が使われたことを確かめる。遅延評価の処理やタイムアウトは、起きていない仕事の数字を出す。

## [8] 報告

結論（速くなった・遅くなった・差が無い・判断できない）を先に書き、数字と単位・回数・範囲・上限を決めているものを1行で添える（例: 「中央値 41ms が 33ms になりました。各7回で、変更後の範囲は32〜35ms。1コアでの JSON の解釈が上限です」）。上限を名指しできない、片方が未調整、4と7を確かめられなかったときは「判断できない」と書き、足りないものを書く。
