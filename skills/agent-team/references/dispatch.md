# dispatch.md — 実装者ルーティングと dispatch / レビュー / 差し戻しの実施手順

Codex呼び出しの構文・失敗処理はすべて `~/.agents/docs/codex-protocol.md`（以下「プロトコル」）が正本。
このファイルはプロトコルを/agent-teamの文脈でどう使うかだけを定める。値や構文をここに複製しない。

**model / effort だけは例外**: /agent-teamでは値の正本は **team.yaml → defaults.yaml** であり、
プロトコル§1の既定・段階制（初回high→再レビューmedium等）は**使わない**（§1冒頭の優先順位どおり。
§1が効くのはルーティング設定でキーが未定義に落ちたときの最終フォールバックのみ）。
プロトコルから借りるのは構文・失敗処理・雛形・規律であって、値ではない。

**読者について**: [4]〜[6]は既定でexecutorサブエージェント（`routing.executor`）が本書の
手順を実行する（SKILL.md [3.5]）。その場合、本書の「Orchestrator」はexecutor自身を指す。
ただしexecutorはサブエージェントを起動できないため、次の読み替えを適用する:
- 「reviewerサブエージェントへ」→ **二重ゲート**に読み替える:
  - ゲート1（独立性）: executorが独立Codexレビューを発注——文書レビュー形(3a)で
    `team-code-reviewer` スキル名指し（**正本 `~/.agents/skills/team-code-reviewer/SKILL.md`
    のパスも併記する**。Codex側のスキル名は `reviewer` で名前が一致しないため、
    名前だけでは解決に失敗しうる）＋契約＋対象パス範囲。新規セッション＝文脈ゼロ・
    ミッション利害なし・作者情報は伏せる。モデル/effortは `routing.codex-review`
    （既定 gpt-5.6-sol / low＝原型のGeneral Reviewer=Sol/low構成の再現）。
  - ゲート2（クロスベンダー）: executor自身が契約適合の機械チェック
    （Allowed paths外変更の`git status`照合）とClaudeの目での品質確認を行う。
  - **実行順序（並列化とラウンド節約）**:
    1. まず契約適合の機械チェックのみ即時実行（違反ならレビュー発注前に即FIX）
    2. ゲート1をバックグラウンド発注し、**待ち時間にゲート2の品質読みを並行実行**
    3. 両判定を統合し、**指摘は1つにまとめて1回のresumeで差し戻す**
       （autodevと同じ「各ラウンド1回・修正は一元管理」。2往復に分けてラウンドを浪費しない）
  - **合格 = 両ゲートともP0〜P2ゼロ**。統合差し戻し1回を1ラウンドと数える。
- 「cc-choreへ委譲」→ executor自身が実行する（ノイジーな出力はexecutorの
  コンテキストに落ち、上位のOrchestratorには届かない——防火壁は成立）
- cc-worker行きタスク・破壊的git操作 → 実行せず上位のOrchestratorへ報告して返す

## ルーティング判定（分解時に契約ごとに上から順に適用）

**[1] cc-worker（coding-agent / opus）行き — Codexの実行環境では物理的に無理・非効率**
次のいずれか1つでも該当:
- 検証にネットワーク・環境構築（npm install等）・実ブラウザ操作が必要
  （プロトコル§13の実測: sandboxはネットワーク遮断・workspace外書込不可）
- Allowed pathsを分解時点で確定できない（探索しながら書く性質）
- 仕様外の設計判断が複数回発生する見込み（NEED-DECISION往復がresume回数を食い潰す）

**[2] hard-worker行き — 腰を据えた推論・広い文脈想起が要る**
[1]非該当で、次のいずれか1つでも該当:
- **実装が新規で複雑**: 追うべきコードパスが複数本 / リポジトリを深く辿る理解が前提 /
  前例のないパターンを組む（状態・エッジケースの盲目的なミクロ判断が多い）。量産モデルはここに弱い。粘らせず最初から上位モデルへ。
  新規UIコンポーネントもこの基準で判定する（複雑性を過小評価しやすいので注意。ただし「UIファイルに触る」こと自体は理由にならない。
  「画面を見ながらでないと決められない」仕事は[2]ではなく[1]=cc-worker）。
- 原因が特定されていないバグのデバッグ
- 失敗コストが高い中枢部（データ整合性・セキュリティ・共有基盤）への変更

**[3] それ以外 → worker（量産既定）**
契約でパスと手順が確定済みの局所的な実装。**既存UIパターンを踏襲する画面変更で
Acceptanceが明確なものもここ**（例: 既存ナビ構造へのメニュー追加、既存フォームへの項目追加）。
7:3で迷ったらworkerに倒す（誤判定は下記エスカレーションで1回で昇格して回収する設計）。

**判定の視点（[2]の誤適用防止）**: 判定は**契約作成後にワーカーへ残る不確実性**で行う。
契約の事前調査が潰した複雑性——行番号付きの確認済み事実・手順化済みのステップ・
先回りで塞いだ罠——は[2]の根拠にカウントしない。**触るファイル数・行数・変更の表面積も
判定材料にしない**（「複数ファイルに触る」≠「複数のコードパスを自力で追う」）。
[2]が守るのは「ワーカーが自力で発見・理解・判断しなければならない」状況であり、
契約が良いほどworkerで足りる——分解と契約が主防壁、モデルの強さは契約の穴を埋める保険。
（実例: 行番号付き事実＋8ステップ手順＋罠の先回りを備えたT-003-01を「触るパスが複数」を
理由にhard-worker判定した誤り。残存不確実性はworker相当だった）

model/effort・並列上限・fixラウンド上限の実値は、スキル側 `references/defaults.yaml`
（正本）をプロジェクトの `.agents/config/team.yaml`（差分）で上書きして解決する。
それでも未定義のcodex系model/effortはプロトコル§1の既定にフォールバック。

## Codexワーカーの起動（実装形）

1. プロンプト組み立て: **冒頭に「`team-worker` スキルを読み、その行動規範に従え」を必ず置く**
   （正本 `~/.agents/skills/team-worker/`。自動発動を当てにせず名指しする）。
   続けてプロトコル§8cの実装依頼雛形 ＋ 契約文書（T-xxx.md）全文。
   契約のVerification欄には「実行できる範囲の自己検証」だけを書く
   （sandbox内で不可能なコマンドを要求しない。ビルドゲートはOrchestrator側の仕事）。
   - その他のCodex側スキル（プロジェクトの `.codex/skills/` 等）を使わせたい場合も
     同様に契約へ名指しで書く（exec実行でもスキルは読めるが、発動判断はモデル任せのため）。
2. 起動: プロトコル実装形(3d)。`-C` はリポジトリ絶対パス、`run_in_background` 必須、
   stderrをファイルへリダイレクトしsession idを回収、`-o` はscratchpadにタスク別ファイル名で。
3. 起動したら session id・出力パス・開始時刻をミッションファイルのTasks表に記録する
   （セッションが死んでも次のセッションが回収できるように）。

## 並列実行の規律

- 同時起動数は team.yaml `routing.worker.parallel_max` まで。
- 並列に流してよいのはAllowed pathsが相互に非交差の契約だけ（分解☑で保証済みのはず。
  dispatch直前に再確認する）。
- 全workerは同一ツリーに書くため、**per-task diffは必ずパスでスコープして取る**:
  `git diff -- <そのタスクのAllowed paths>`。全体diffでレビューしない（他タスクの変更が混ざる）。
- **テスト・ビルドの結果も同一ツリーで汚染される**（diffと違い `--` でスコープできない）。
  `npm test`/`build` の失敗を見たら必ず「自分のタスク起因か他タスクのWIP起因か」を切り分ける。
  **変異スモークは全体suiteで判定せず、対象タスクのテストファイルの単体実行で前後比較する**:
  変異前に単体実行で緑を確認→変異→同じ単体実行が赤に転ぶことを確認→復元。
  単体実行でも基準が緑にできない（他タスクWIPが波及している）場合のみ、静まるまで延期する。
  他タスク起因の赤を「変異を捕まえた」と誤読すると**偽の安心**を生む——検証しないより悪い。
- **集約ファイル**（`package.json` のtestリスト、ルート定義、index的な再エクスポート、CI設定等、
  複数タスクが1行ずつ追記したくなるファイル）は**どのタスクのAllowed pathsにも入れない**。
  分解時に特定し、契約には「登録はOrchestratorが行う」と書いてworkerには成果物本体だけを作らせる。
  登録の1行は**そのタスクの合格commitに同梱してOrchestratorが書く**（commitはもともと直列なので
  衝突せず、独立工程にしないことで登録忘れ＝沈黙する欠落も防ぐ）。
- event駆動: あるタスクの完了→即レビュー→即、依存が解けたタスクのdispatch判定。
  同グループ他タスクの完了を待たない。

## 監視

- バックグラウンド完了通知で回収する。ポーリングしない。
- ハング疑い（通知が長時間来ない）: stderrログを確認し、プロセス生存を確認。
  死んでいたらプロトコル§6の失敗時ハンドリング（1回だけ再実行→ダメなら中断報告）。
- usage limit系エラー: 実装用途はプロトコル§13の例外に従い即中断ではなく
  Orchestratorに戻して判断（cc-workerへのフォールバック可）。

## レビュー（Codex実装分）

1. worker完了 → 変更をパススコープdiffで取得し、契約適合を先に機械確認:
   - Allowed paths外の変更が `git status` に無いか（あれば即FIX、理由を添えて差し戻し）
   - NEED-DECISIONが返っていないか（あればOrchestratorが判断を解決してresumeで返す。
     プラン・既存決定から自答できない設計判断だけ人間に確認）
2. reviewerサブエージェント(opus)へ: 契約文書＋パススコープdiff＋workerの最終メッセージを渡す。
   作者がCodexであることは伝えない（プロトコル§13レビュー独立性）。
   判定形式はreviewer定義に従う（VERDICT + P0〜P3 + 証拠必須）。
3. P0〜P2があればFIX: 指摘を整形してresume形(3c＋sandbox指定。フラグ位置はプロトコル3dの注意書き通り)で差し戻し。
4. 合格（P2以上ゼロ）→ レビュー結果を `queue/reviews/T-xxx.md` に保存 →
   Orchestratorがtask commit: `git add <Allowed paths> && git commit -m "T-xxx: <summary>"`。

**レビューループの定義（実装者を問わず共通）**
- 合格ライン: **P0〜P2がゼロ**（P3のみは合格。対応は任意で残課題に記録）。
- 1ラウンド = FIX差し戻し→再実装→再レビュー。差し戻し回数の上限が
  `limits.fix_rounds_task`（既定3）。**3回目の修正後の再レビューでもP2以上が残ったら、
  それ以上差し戻さずOrchestratorへエスカレーション**（下記§エスカレーション）。
- 再レビューの担当: 初回と同じレビュアーに文脈を保持して依頼する
  （CC reviewer → SendMessageで同一エージェント / Codexレビュー → resume形）。
  再レビューはプロトコル§8bの二点評価——①前回指摘への対処が十分か
  ②修正で新たに入り込んだ問題が無いか——を独立に行わせる。

## レビュー（cc-worker実装分）

- coding-agentの完了報告後、Codexにレビューさせる。**文書レビュー形(3a)で
  「`team-code-reviewer` スキル（正本 `~/.agents/skills/team-code-reviewer/SKILL.md`）を読み、
  その手順・出力形式に従え」＋契約文書＋対象パス範囲を
  プロンプトで渡す**（組み込み差分レビュー(3b)はカスタムプロンプト不可のため、
  スキルと契約文脈を効かせられない。差分はteam-code-reviewerの手順に従いCodex自身に取らせる）。
- モデル/effortは `routing.codex-review`（既定 sol/low）。
- 合格ライン: cxloopと同じ（P2まで全クリア。VERDICTとタグの解釈はプロトコル§7）。
- FIXはSendMessageで同一coding-agentへ差し戻し（文脈保持）。
- 合格後のtask commitは同上（coding-agentが自らcommit済みならそれを検証するだけでよい）。

## 調査dispatch（既定=Codex）

- 既定は codex exec への委譲（`routing.research`）。呼び出しは文書レビュー形(3a)と同じ構文で、
  プロンプト冒頭に「`team-researcher` スキル（正本 `~/.agents/skills/team-researcher/SKILL.md`）を
  読み、その行動規範に従え」＋調査質問・対象範囲・除外範囲・必要な根拠形式。
- 読み取り専用の依頼なのでsandbox指定は不要（既定のまま。書込権を渡さない）。
- **並列fan-outと意図的重複**: 独立な調査は並列に投げる（`parallel_max`まで）。
  結論に効く重要領域は、複数依頼のスコープを意図的に重複させる——
  同じ箇所について矛盾する報告が返ったら、それは誤報検出のシグナルであり、
  必ず自分で裏取りしてから採用する。
- **CC researcherへのフォールバック**（`routing.cc-research`）:
  (a) 人間がCC委託を明示した場合。
  (b) Codexがusage limit / quota系エラーの場合——プロトコル§6(d)に従いリトライせず、
      その依頼と以後の同一ミッション内の調査をCC側へ切り替える（回復はミッション単位で判断）。
- 委譲先を問わず、報告には[read][grep][inferred]ラベルと否定形主張の検索記録を要求し、
  **第1.5層の検証プロトコル**（証拠なし主張の破棄・結論に効く主張と否定形主張の裏取り）を
  適用してから採用する。

## 雑務の委譲（原則Codex worker、不可のものだけcc-chore: haiku/xhigh）

Orchestrator（高価格モデル）のコンテキストと単価を、ノイジーな機械作業から守るためのレーン。

**委譲先の選択（上から順）**:
1. **原則: Codex（`routing.worker`の設定で codex exec）** — ChatGPT Pro枠で処理し
   Claude枠を温存する。読み取り調査系・workspace内の収集/整形/一括変換など。
2. **cc-chore（Agentツール: general-purpose / haiku / effort xhigh）** — 次の
   **Codex環境起因で不可**の雑務のみ:
   - git書込操作（commit・branch・worktree整備・復元。sandboxは`.git`読取専用）
   - workspace外のファイル・ネットワークが必要な作業
   - **実行証拠が要る検証＝完了ゲートの実行**（プロトコル§10: Codexのlint/test
     実行挙動は不定で「passed」主張は証拠にならない。CC側subagentは実ツール実行の
     記録が残るため証拠になる）

**判定基準は圧縮率**——「中間出力が長く、結論は短い」仕事だけ委譲する:
- ✅ 委譲する: 完了ゲートの実行（→cc-chore）、複数手順のgit整備（→cc-chore）、
  ログ/成果物の収集整形・大量ファイルの機械変換（→Codex worker）
- ❌ 委譲しない: 単発コマンド（git status 1回、ファイル1個の確認）。
  委譲指示文の方が高くつく（グローバルCLAUDE.md「小さな確認は自分で」と同じ原則）

**依頼の作法**:
- 指示は短く具体的に（実行するコマンド列・作業ディレクトリ・欲しい報告形式）。
  長い指示文はOrchestrator価格の出力なので、ここが膨らむと委譲の意味が消える。
- 報告形式を強制する: 「各コマンドのexit code＋失敗時のみ出力末尾30行。成功時は1行」。
  「passed」の散文報告だけを信用しない——exit codeを証拠として要求する。
- 破壊的操作（削除・reset・force系）を含む雑務は委譲せずOrchestratorが自分で実行する
  （判断を伴う操作は雑務ではない）。

## エスカレーション（fix_rounds_task 超過時）

Orchestratorが差し戻しログから原因を判断して切り替える。同一workerセッションを続投させない。

- (a) 文脈想起の不足（広い参照が要ることが判明）→ hard-workerへ再割当。
  新規契約・新規セッションで、前ラウンドの失敗の要約を契約Contextに含める。
- (b) 契約の曖昧さ（Goal/Acceptanceの解釈が割れた）→ 再分解。契約を書き直す。
- (c) 環境制約（検証にネットワーク等が必要と判明）→ cc-workerへ切替。
- 切替もラウンド消費とみなし、ミッション全体で同一タスクに2回切替が起きたら
  人間へ報告して方針を仰ぐ（設計に穴がある兆候）。報告時の選択肢には
  **gpt-consultスキルによるGPT Pro相談パッケージ作成**を含めてよい（原因仮説が尽きた場合は特に）。
