# Codex のモデル比較（sol / luna）— レビューと実装の実測（2026-09-25〜26）

Codex の週間上限を3日で使い切りそうになったのを受けて、モデル・effort の選び方を実データで比べた記録。
モデル・effort・ハーネスを変える判断をするときは、ここを起点にして、必要なら同じ方法で測り直す。

## 結論

- **luna max は、sol の代わりのレビュアーにも実装者にもならない**（品質を今の95%以上に保つ前提）。
  - レビュー: 親が差し戻しに入れた指摘の拾い漏れが多い（sol medium 83% に対して luna max 50%）。
  - 実装: 1回目のレビューでの指摘が約1.8倍（sol high 9件 → luna max 16件）。契約の誤りに自分で気づく力も弱い。
- **luna の上限上の重みは sol の 1/5〜1/20（1/10前後が有力）**。ただし同じタスクでトークンを sol の約3倍使うので、実装の実費は sol high の約2〜5割にとどまる。「1/20 の費用」にはならない。
- **luna の使いどころ**: 調査（research）、小さく明確なタスク（express）。レビューでは sol と見落としの傾向が違う（Claude の reviewer だけが見つけた3件のうち2件を拾った）ので、2本目のレビューとしての可能性はある。ただし根拠が3件しかなく、未検証。

## 1. レビューの比較（7タスク）

- 対象: 個人開発の RPA 管理アプリ（Next.js の hub ＋ C# の agent）の過去タスク T-1903・T-1904・T-2001〜T-2005。当時の1回目のレビューは gpt-6-sol medium。
- 方法: 比較元のコミットに当時の差分パッチ（記録の sha256 と一致を確認）を当てて状態を再現し、同じ依頼文を gpt-5.6-luna max に渡した。
- 正解: 親が裏取りして差し戻しに入れた P2 以上（sol と Claude の reviewer の和集合）の18件。

| 正解の出どころ | 件数 | sol medium | luna max |
| --- | --- | --- | --- |
| sol と Claude の両方 | 3 | 3 | 2 |
| sol だけ | 12 | 12 | 5 |
| Claude の reviewer だけ | 3 | 0 | 2 |
| 合計 | 18 | 15（83%） | 9（50%） |

- sol の指摘自体が正解に入っている分、sol の数字は有利に出ている。
- luna は T-2003 で重要な2件をどちらも見逃し、T-2005 ではテストの不足について逆の判断をした（「変異 M6 を検出できる」としたが、親は sol の指摘どおり不足と認めて直させていた）。
- 正解リストにない luna だけの指摘にも正しいものがあった（T-2003: 1行の例外で残りのスケジュールがすべて処理されない。当時のコードで確認）。

## 2. 実装の比較（4タスク）

- 対象: 同じアプリの T-1903・T-2002・T-2003・T-2004。当時の実装者は gpt-6-sol high の Codex worker。
- 方法: 実装前の状態を再現し、当時と同じ依頼文（Codex の記録と完全一致を確認）を luna max に渡した。判断待ち（NEED-DECISION）には当時と同じ親の回答を渡した。採点は、モデル名を伏せて、当時と同じ sol medium のレビュアーと依頼文で行った。

| 観点 | sol high（当時） | luna max |
| --- | --- | --- |
| 1回目のレビューの指摘（P0〜P2） | 9件（P1 1件） | 16件（P1 1件） |
| 本人の検証（lint・型検査・全テスト・ビルド） | 全件通過 | 全件通過（Codex の記録で確認） |
| 契約の穴への気づき（T-2002） | 矛盾を2件とも質問した | 1件だけ質問し、もう1件（契約の誤り）どおりのテストを書いた |
| 親が C# のテストを流した結果（T-2002） | 990件中1件失敗 | 989件中1件失敗 |
| 初回実装の費用（週間枠） | 1タスク約1.1%（手戻り込み約2.1%） | 1タスク約0.5〜0.7% |

- luna の実装に多かった指摘: 契約が求めるテストの抜け（二重送信・失敗時の表示など）、境界の条件での誤動作。
- 指摘が増えると、sol のレビュー（1回約0.18%）と手直しの往復が増え、初回で浮いた分の大半が相殺される。往復ごとに親（Claude）の統合作業と Claude の reviewer も増える。

## 3. luna の重みの推定

| 手がかり | 結果 |
| --- | --- |
| 上限の使用率の記録（9/23〜25、約7000点）への当てはめ | luna の重みを sol と同じにすると予測のずれ 1.1 ポイント、1/5 だと 0.7、1/20 だと 0.76。1より小さいのは確実だが、1/5 と 1/20 は区別できない |
| レビュー7件（luna だけが動いた時間帯） | sol 換算 8.0% のトークンに対して、使用率の増加は約1% |
| 実装4件 | sol 換算 15.2% のトークンに対して、使用率の増加は約2〜3% |

- 仮定: キャッシュされた入力は0.1倍、出力は8倍（API 料金で一般的な比率。GPT-6 での実際の比率は未確認）。
- 使用率は整数でしか記録されないので、1回の観測の誤差は ±0.5〜1 ポイントある。

## 4. 関連して分かったこと（2日分の実績。重みは luna 1/20・出力8倍）

- 消費の内訳: 実装 51%・コードレビュー 30%・計画レビュー 9%・調査 9%。**全体の45%が手戻り**（2回目以降の手直しと再レビュー）。
- 1回あたりの消費（sol high の実装1回を1.0とした比）: コードレビュー high 0.47 → medium 0.26、計画レビュー high 0.50 → medium 0.24、調査 sol high 0.80 / luna max 0.12。effort を medium に下げると、レビュー1回の消費は約半分になる。
- 実装の手戻りのきっかけ: レビューの差し戻し 79%・契約の不足による判断待ち 11%。差し戻しの指摘を契約と突き合わせると、契約に書いてあるのに満たしていない 42%・当然気づくべき境界の見落とし 31%・計画の穴 11%・テストの検出力 11%。
- 指摘の実益（3プロジェクト87件）: 実益あり 78%・起こりにくいエッジケース 13%・重箱の隅 8%・オーバーエンジニアリング 0%。細かい指摘は2回目以降の P2 に集中していた（1回目の P2 は21%、2回目以降の P2 は47%）。

## 5. この比較を受けて決めたこと（2026-09-26 時点）

- worker は gpt-6-sol medium のまま（luna max にしない）。codex-review は gpt-6-sol medium、research は gpt-5.6-luna max。値の正本は `~/.agents/skills/agent-team/references/defaults.yaml`。
- 実装者に「報告前の契約照合」を必須化（`~/.agents/skills/team-worker/SKILL.md`）。
- 重大度の基準を明確化し、起こりにくく影響が中以下のものを P3 にした（`~/.agents/docs/review-severity.md`）。

## 6. 測り直すときの方法と注意

- 消費: `~/.codex/sessions/**/rollout-*.jsonl` の `token_count`（`last_token_usage` と `rate_limits.primary.used_percent`）を、セッションの `turn_context` のモデルごとに集計する。クラウドで動いた Codex の分は手元の記録に残らない。
- 比較の条件: 過去タスクの比較元コミットと差分パッチ（レビュー記録に sha256 がある）で状態を再現し、当時の依頼文をそのまま使う（依頼文は Codex の記録の最初のメッセージと照合する）。依存パッケージ（npm ci・dotnet restore）は親が事前に入れる。
- 公平さ: 採点のレビュアーにモデル名を伝えない（フォルダ名・報告の中のパスも中立にする）。実装の結果は `cx_evidence.py --worktree` で記録から確かめる。
- 限界: 各タスク1回ずつの実行で、レビュアーの判断にもぶれがある。「明らかな差があるか」を見る精度しかない。重みの推定は、実行中に他の Codex の利用がない時間帯を選ぶと精度が上がる。
