# /agent-team — チーム開発の共通手順

## 適用範囲

agent-teamで進行中の開発は、後続の追加実装・修正・再開にも明示指定なしで継続適用する。無関係な依頼や軽微な変更は対象外とする。

## 原則

- 現在のセッションがOrchestrator。親モデルの切替で品質条件は変えない。計画・割当・受入・状態管理を担当し、実装はworkerへ委譲する。
- サブエージェントは事前定義を使う。セッションごとのモデル選択やdispatchごとの設定照合は追加しない。
- 通常ミッションの計画・コードは独立レビューと別ベンダーの視点を確保する。担当の組合せはハーネス用ラッパーに従い、実装者の自己承認は禁止する。expressは `references/express.md` に従う。
- 指標はミッションの精度と完遂速度の両方。依存も競合資源も無い作業はタスクでもミッションでも並列で進める（[1]「ミッションの並列」、dispatch「並列実行の規律」）。
- 契約、レビュー、統合後の検証が揃うまで完了としない。現在の要件を満たす簡潔な実装を選び、既存機能を再利用する。
- 状態はファイルに保存し、上限・書込権は `references/state-layer.md` に従う。
- 人間に判断を聞いたら、答えが来るまでその判断に左右される箇所は実装・dispatchしない（推奨案での先行実装もしない）。左右されない作業は続け、何を止めて何を続けているかを質問に添える。ハーネスやプロジェクトの既定が「推奨で進める」でもこれを優先する（R9）。
- 人間に報告・質問するたびに（計画の承認依頼・判断待ち・status・最終報告）、状況ページを更新してURLを添える。手順は `references/templates/REPORT_TEMPLATE.md`「状況ページ」。

## 読み込みと設定

1. Claude Code用ラッパー `~/.agents/claude/skills/agent-team/SKILL.md` を読む（既読なら不要）。進行役はClaude Codeだけで、Codexが読んだ場合は通常の作業として進める（R9）。
2. 本流・resumeでは `references/defaults.yaml` と `.agents/config/team.yaml` を読む。設定の解決はラッパーに従う。
   会話の圧縮後・別の会話での継続時も次のdispatch前に1回読み直し、要約や前の会話に残ったmodel・effortは使わない。
3. `.agents/state/STATE.md` → 対象ミッション → `.agents/state/MEMORY.md`。履歴全量は読まない。
4. 工程に必要な資料だけ読む: 分解・実行はdispatch、[4]〜[6]はexecute、S判定はexpress、状態操作はstate-layer、契約作成はtemplates、作業の型は `references/types/README.md` と選んだ型のファイル。実行プロトコルは該当経路だけ読む。
   dispatchと契約の雛形は、既読でも**ミッションの[3]を始めるたびに読み直す**（R8）。

作業ツリーに `.agents/` が無ければ `git log --all --oneline -- .agents` と既定ブランチの状態ファイルを調べる。履歴にあれば敷設済みとして対象commit/PRを特定し、復元・統合を人間に提案する。履歴にも無い場合のみinitを提案する。
Git操作は `~/.agents/skills/git-ops/SKILL.md` に従う。

## モードと規模

| 呼び出し | 動作 |
| --- | --- |
| `/agent-team {依頼}` | 前提確認・intake → S/M/L判定 |
| `/agent-team init` | `references/init.md` の敷設手順 |
| `/agent-team status` | 行数とSTATE/BACKLOG/queueを読み、`references/templates/REPORT_TEMPLATE.md` の順で報告するだけ（整理・記帳・commitはしない。状況ページの更新だけは行う） |
| `/agent-team resume` | 下記の引継ぎ手順 |

- **S / express**: 対象ファイル確定、設計判断不要、diff一読でレビュー可能。`references/express.md` へ。
- **M**: 分解不要だが契約・独立レビューが必要。1タスクで下記工程を回す。
- **L**: 依存する複数タスクへ分解し全工程を回す。
- **ミッションの単位**: 1つのPRで出せ、Acceptanceを1回の統合ゲートで確かめられる成果。目安（台帳で見直す仮置き）はタスク3〜8件・依存の深さ3まで・途中で人間の判断が要らないこと。
  - 分ける: 別々に出荷できる成果が混ざる／目安を超える／前提のスパイクが要る／途中で人間の判断が要る／共有基盤とそれを使う機能が同居する。スパイクと基盤は先のミッションにし、判断の地点で区切る。
  - まとめる: 同じ領域で1タスクのMや小さなBACKLOG項目が並ぶときは、1ミッションにまとめる。

## ミッションフロー

各工程の完了条件を満たしてから次へ進む。未達はミッションとSTATEのBlockersに記録する。

### [0] 前提確認
- 設定と状態を読み、`bash ~/.agents/skills/memory-ops/scripts/check-size.sh` で計測する。
- 閾値超過は `~/.agents/skills/memory-ops/SKILL.md` に従い整理する。閾値+10%未満のみ[7]へ先送り可。
- 閉じたのに台帳に無いミッションを記録する: `python ~/.agents/skills/agent-team/scripts/mission_cost.py <リポジトリ> --missing`。
- 完了条件: 必須設定・状態が読め、上限内または許容された先送りである。

### [1] Intake
- 作業の型を `references/types/README.md` の表で作業の中身から選び（当たるものは全部）、選んだ型のファイルを読む。ミッションの `型:` に書く。
- `bash ~/.agents/skills/explain-page/scripts/list.sh <リポジトリ> 設計判断` で過去の設計判断を見て、関係する決定はミッションの制約に `E-xxx` 付きで書き、食い違う依頼は進める前に人間に確かめる。判断待ち（`Status: open`）はexplain-pageの「判断待ちを閉じる」に従い、Intakeの確認と一緒に聞いて閉じる。
- Goal、検証可能なAcceptance、制約、Human Escalationを確定する。不明点だけ人間に確認する。分ける・まとめるは「ミッションの単位」に照らしてエージェントが決め、理由をミッションファイルのLogに1行書く（人間には聞かない）。
- `references/templates/MISSION_TEMPLATE.md` からM-xxxを採番し、STATEに索引を追加する。
- ブランチはgit-opsの命名に従う（例: `feat/m-xxx-summary`）。
- **ミッションの並列**（R10）: 依頼が複数のミッションになる、またはSTATEに他のactiveミッション・BACKLOGに着手可能な独立項目があるときは、親がタスクと同じ規則でミッション同士の並列計画を立てる。依存も競合資源（触るファイル・DB・ポート等）も無いミッションは人間の指示を待たずに同時に進め、一部だけ重なるなら重なる所だけを後にする。
  - 人間の「A → B → C の順に」「順次」は優先の順番と読む。直列にするのは、人間が「1本ずつ」など直列を明示したときだけ。
  - 同じセッションの中で同時に進めるミッションは、ミッションごとにworktree・ブランチ・進行管理者を分け、M-IDの採番とSTATEは親だけが書く。人間が別のセッションで並走させるときは、各セッションは自分のミッションのファイルとSTATEの自分の索引行だけを書く。
  - あるミッションが人間の判断待ちでも、その判断に左右されない他のミッションは止めない。
- 完了条件: 成功条件と作業範囲を文書化した。

### [2] 調査（必要時）
- 調査担当へ `~/.agents/skills/team-researcher/SKILL.md`、質問・範囲・除外範囲を渡す。型があれば型の「調査の問い」を質問に入れる。
- 重要領域は意図的に重ねて調べ、矛盾を検出する。報告の採用規律はdispatchを参照。
- 読み取り専用担当の結果は親が `queue/research/` に保存する。
- 誤っていると計画全体を覆す前提は、権限内の小さな実験で検証する（根拠R1）。
- 完了条件: 判断に使う主張に根拠がある。

### [3] 分解・計画レビュー
- Goal / Acceptance / Allowed paths / 依存 / 実装者を骨子にする。Acceptanceを書き終えたら `references/types/README.md` の表で型を選び直し、型の対応表を埋め、`scripts/check_types.py` を流す（R13）。型があれば型の「契約の既定欄」を入れる。契約はdispatch前に `GENERAL_TEMPLATE.md` へ清書する。
- テストを書く契約では、骨子段階から変異リスト（**どのファイルのどの箇所を何に変えるか**）を作る。機構の削除・置換では維持すべき挙動、CI・デプロイ・戻し（復旧）の仕組みも変異の対象にする（R2）。
- 契約の参照関係表（生産者/消費者）を骨子段階から埋める。表の効果は数ミッション後に件数で点検する（R3）。
- `references/dispatch.md` で担当を選び、依存とAllowed pathsからステップ（同時に起動できるタスクの組）を組む。作業ツリーの競合とレーン分けはdispatch「並列実行の規律」に従う。
- レーンを分けるなら、レーンごとの担当ファイル群・ブランチ・worktree・進行管理者と、合流の順序・合流後の再検証を並列計画に書く。
- 別ベンダーの独立担当へ `~/.agents/skills/team-plan-reviewer/SKILL.md` と分解文書を渡す。初回は `~/.agents/skills/team-plan-probe/SKILL.md` と文書パスだけでprobeも並走させる。ズレは**曖昧箇所の候補**として確かめ、初回修正へまとめる。probeは合否に数えない。
- レビューの合格・版記録・再レビュー（計画の指摘の直し方を含む）はdispatchに従う。上限は `limits.fix_rounds_plan`。
- 指摘が修正起因か以前から存在かを区別し、修正起因が過半なら分解を見直す。上限超過時は文書の矛盾／実験が必要／上流設計の判断に分けて、再分解・スパイク・gpt-consult等の選択肢を人間に提示する（R1）。
- 分解と並列計画は人間の承認を1回得る。既存の承認範囲内で同じ確認を繰り返さない。
- 分解後に目安（タスク8件・依存の深さ3）を超えたら、承認を頼む前に分けるかを決め、理由をLogに1行書く。分けたら各ミッションの計画を承認に回す。
- 完了条件: 契約・計画レビュー・承認と並列計画が揃った。

### [3.5] 進行管理の委譲（該当時）
- ラッパーの節約運用が該当すれば[4]〜[6]をexecutorへ委任する（STATEの縮約・人間の判断・破壊的操作の判断は親に残す。詳細はラッパー）。使えなければ親が進行管理する。委任しても実装者・レビュー条件は変えない。

### [4]〜[6] 実行・レビュー・統合
- 手順は `references/execute.md`。読むのは親が直接進行管理するときだけ（委任時はexecutorが読む）。
- 親が受け取るときの完了条件: 全タスクの報告・最終版に紐づく合格・検証証拠・画面確認の記録（該当時）・型の[6]検証の記録（該当時）・task commit、統合後HEADでの `verify.post_change` / `verify.smoke` の実行記録、変異証拠が揃った。

### [7] 受入・状態整理
- Acceptanceと証拠を照合する。フロントエンドは実描画を確認する。親の差分確認は要件に直結する範囲を抜き取り、独立レビュー全量を機械的に繰り返さない。
- 必須レビュー未達はdispatchの縮退規則に従い、通常のdoneにしない。
- 戻し（復旧）の受入では、戻した版が戻す前と別物であることを実行記録の版（SHA 等）で確かめ、「戻し成功」の表示だけで受け入れない。
- 人間の要望に穴を残す見送りP3は、最終報告の「例外受入・残課題」に必ず載せ、「例外受入なし」と書かない（R14）。
- 別の作業を理由に先送りした項目は、閉じる前に理由が残っているか確かめ、解けていれば片付けるかBACKLOGに積み直す。
- 人間の指摘・エスカレーション・NEED-DECISIONがあったミッションと、同じレビューの修正が上限（`limits.fix_rounds_*`）に達したミッション（最後のレビューの合否は問わない）は、閉じる前に `~/.agents/skills/reflect/SKILL.md` で振り返り、採用・却下・保留の表をミッションファイルに書く。採用案の反映は人間の承認を待つので、[8]の判断待ちに「改善案 N 件の反映」として1件で載せ、表のパスを添える（R11）。
- state-layerに従いSTATEのLogを1行に縮約し、sessionをクリアしてから、ミッションを `bash ~/.agents/skills/agent-team/scripts/close-mission.sh <M-ID> [<作業場所>]` で閉じる（移動・画像の掃除・台帳記録をまとめて行う。手で移さない）。教訓はmemory-opsの入口に従う。
- 行数を再計測し、必要な整理と状態commitを終える。PR希望時はミッション単位で作成し、作成の直前に git-ops を読んで合わせる。
- 完了条件: 受入証拠と引継ぎ可能な状態が揃った。

### [8] Closeout・最終報告
- git-opsに従いミッション由来の一時worktree・統合済みブランチを後片付けする。
- 未統合・ロック等で保持する場合は理由と次の削除条件を記録する。
- 台帳（`~/.claude/agent-team-ledger.jsonl`）への記録と画像の掃除は[7]の `close-mission.sh` が済ませている。改善の効果はこの台帳で精度と完遂速度の両方を前後比較する。
- 最終報告は `references/templates/REPORT_TEMPLATE.md` の順番で書く。
- 完了条件: `close-mission.sh` の出力の1行（台帳の記録）と、後片付けの結果を載せた最終報告を出した。

## resume
1. STATEと対象ミッションを読む。複数activeなら対象を確認する。
2. 他sessionのActive sessionが残る場合は二重運転を警告し、人間が引継ぎ可否を判断するまで記帳・整理しない。
3. 上限を計測・整理し、自sessionを記録する。Tasks/Next actionsから再開する。
4. 未回収の担当は記録したsession・報告・ラッパーの継続手段で確認する。未回収を完了扱いにしない。

## 禁則・参照
- 契約なしのdispatch、workerによるgovernance編集、権限回避、未実行の合格報告（原則「本物で確かめる」）は禁止。
- workerのgovernance禁止には `.agents/`、AGENTS.md、CLAUDE.md、ハーネス設定を含む。
- 規則の実測背景は `references/evidence.md`（必要時のみ）。
