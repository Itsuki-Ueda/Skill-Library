# 振り返りをイシューにする

対象は、まとめ役の表の「採用」のうち行き先がスキル（説明文の調整・新しいスキルを含む）の行と、「保留（仕組みで止めるもの）」の行。
1回の振り返りで「判断待ち」として立てるのは3件まで。残りは「候補」のイシュー1件にまとめる。人間が判断する件数を抑え、1回きりの指摘は2回目が来るまで判断に上げないため（INBOX と同じ考え方）。
イシューは人間が読んで採否を決める材料なので、1行の要約で済ませない。まとめ役の「詳細」から、実際に起きたことを具体的に書く。

## 1. 同じ指摘を探す

```bash
repo=$(head -n1 ~/.config/skill-library/reflection-repo)
gh issue list -R "$repo" --label reflection --state open --search "{スキル名}" --json number,title,url
```

- 同じ問題を同じ場所で直す案が「判断待ち」で開いていれば、新しく立てずにコメントを足す。本文の先頭は「2回目」（3回目以降はその回数）にして、下の「何が起きたか」と「出どころ」だけを書く。3件の枠は使わない。
- 「候補」のイシューの行に同じ案があれば、2回目なので単独の「判断待ち」として立てる。本文の先頭に「2回目」と書き、「何が起きたか」に前回の行の出来事も書く。候補の行は `→ #{新しい番号}` に書き換える。これを3件の枠に先に入れる。
- 似ているが直す場所か直し方が違うなら、別の案として扱い、立てるときは本文の最後に `関連: #{番号}` を書く。

## 2. 3件を選ぶ

- 同じ変更で直せる案（同じスクリプトの直し、同じ節への書き足し）は、先に1件にまとめる。
- 残りの枠を、次の作業でまた起きる見込みと、起きたときの手戻りの大きさが大きい順に埋める。文章より仕組みで止める案を先にする。
- 「おすすめ」は全部を「反映する」にしない。枠に入れたものの中でも、迷うものは「保留」と書く。

## 3. 新しく立てる

```bash
gh issue create -R "$repo" --label reflection --label 判断待ち \
  --title "{スキル名}: {何をどう変えるかを1行で}" --body-file {本文のファイル}
```

ラベルが無いと失敗する。そのときは一度だけ作ってから出し直す。

```bash
gh label create reflection -R "$repo"; gh label create 判断待ち -R "$repo"; gh label create 候補 -R "$repo"
```

本文は次の見出しをこの順で全部書く。

```markdown
## 何が起きたか
{「何をした→何が起きた」の形で、記録の中の実際の出来事}

## 放っておくと
{次の作業で何に困るか。どんな場面でまた起きるか}

## どう変えるか
{スキルに足す・書き換える文そのもの、または足す検査（作り・型・lint・CI・テストのどれで止めるか）}

## 入れる場所
{スキルのパスと節。仕組みで止めるならその種類}

## 出どころ
{リポジトリ名、ミッション番号（あれば）、日付}

## おすすめ
{反映する / しない / 保留} — {理由を1文}
```

- 書いた人はイシューの作成者として残るので、本文には書かない。
- 顧客名・案件名・秘密の値・業務コードの抜粋は書かない。必要なら「{業務リポジトリA}」のように抽象化する。

## 4. 残りを候補にまとめる

枠に入らなかった案は、振り返り1回につき1件の「候補」のイシューにまとめる。1案1行で、後の振り返りが同じ案を探せるように、スキル名と案を先に書く。

```bash
gh issue create -R "$repo" --label reflection --label 候補 \
  --title "候補: {出どころのミッション} の残り {N} 件" --body-file {本文のファイル}
```

```markdown
- {スキル名}: {何をどう変えるかを1行で} — {何が起きたかを1文}
```

本文の最後に `## 出どころ` を書く（判断待ちと同じ）。
