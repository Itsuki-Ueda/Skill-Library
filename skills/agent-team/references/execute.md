# [4]〜[6] 実行・レビュー・統合

[3]で承認された契約と並列計画から進める。読むのは進行管理者（executorか親）。

ミッションの Log は `bash ~/.agents/skills/agent-team/scripts/log.sh <M-ID> "<内容>"` で足す（時刻を手で書かない）。

## [4] Dispatch
- 契約全文と役割スキルを名指しし、ラッパーの起動方法を使う。レーン運用ではレーンのworktreeを作業場所に指定する。session ID、成果物パス、作業場所、開始時刻を記録する。
- 並列にできるタスク（dispatch「並列実行の規律」）は同じステップで同時に起動し、完了通知ごとに次を判断する（バッチ全体の終了を待たない）。
- 完了条件: 各タスクが起動済み、または依存待ちとして記録されている。

## [5] コードレビュー・修正
- worker報告を親が `queue/reports/T-xxx.md` に保存し、対象差分・新規ファイル・契約適合を確認する。
- 集約ファイルの登録があれば、親がレビュー前に追加する。**登録を含む最終変更**をレビュー・検証し、合格commitへ同梱する。
- `~/.agents/skills/team-code-reviewer/SKILL.md` を独立担当に渡す。指摘は満たすべき性質を示して元のworkerへ差し戻す（R4）。
- 再レビュー・版の更新・上限超過はdispatchに従う。
- 指摘を「今回の変更より前からある問題」として見送るときは、最終報告で人間に伝え、BACKLOGに積む。黙って見送らない。
- テスト契約は進行管理者が変異を1〜2件抜き取り実施し、workerの証跡と照合する（R2。手順はdispatch）。
- 合格内容と実ファイルの一致を確認し、親が対象パスをstageしてtask commitする。未レビュー変更を混ぜない。
- 完了条件: 報告・版に紐づく合格・検証証拠・画面確認の記録（該当時）・task commitが揃った。

## [6] 統合・完了ゲート
- タスク間に接続・共有資源・順序依存があれば、統合後の整合性を独立レビューで確認する（既存レビューに組み込んでよい）。要否は表でなく契約と実際の変更で決める。
- レーンは計画の順序で合流させる。未コミット変更ゼロを確認し、統合後HEADで `verify.post_change` と `verify.smoke` を実行する（実時間依存のテストはdispatchに従う）。
- ミッションの `型:` に型があれば、そのファイルの「[6] 検証」を完了ゲートに含める。
- ミッションの差分に `.github/workflows/` が含まれる場合は、統合後HEADで `uvx zizmor --offline --min-severity high .github/workflows` を実行し、終了コード0を合格とする。
- テストを書いた場合は、[5]で未実施の変異を数件抜き取り、失敗→復元を確認する（[5]から対象不変なら不要）。
- 実行担当はラッパーに従う。実行証拠はdispatchの形式で残し、実行の有無と検証内容の適切さを別々に確認する。
- 失敗は原因を切り分け[5]へ戻す（ゲートを緩めない）。原因不明のまま閉じるなら報告とPRに「未確認（仮説）」と書き、同じ書き方の箇所をgrepしてBACKLOGに積む。
- 完了条件: 最終版に対する必要なレビュー・実行検証・変異証拠が揃った。
