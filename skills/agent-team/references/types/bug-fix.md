# 作業の型: 不具合修正

この型は、自分の見出しにある段の中身を決める。見出しの無い段は共通本体どおりに進める。
主に使う原則: 根本原因を直す（`~/.agents/docs/principles/fix-root-causes.md`）、本物で確かめる、前提を疑う。

## [1] 受付

- 人間の報告から「再現の手順・期待した結果・実際の結果」を1行ずつ書き出す。足りない分は試して埋める。
- Acceptance の1行目は「元の再現手順で、期待した結果になる」にする。

## [2] 調査の問い

調査担当に次を渡す（小さければ親が確かめる）。

1. 再現できるか。最小の再現条件は何か（入力・状態・環境を1つずつ外して確かめる）。
2. 原因の候補を挙げ、観察で半分ずつ外して1つに絞る（推測で絞らない）。値が見えなければログを足して動いているときの値を読む。
3. 症状の出た場所ではなく、最初に間違えた場所はどこか。そこを通るほかの呼び出し元でも同じ不具合が出るか。
4. 回帰なら、いつ、どの変更から壊れたか（git log・git bisect）。
5. 遅い・止まる・メモリが増える不具合は、プロファイル・トレース・ログを取って関数と行まで落とす（既にあればそれを読む）。

- 同じ前提の原因候補が2回外れたら、前提を疑う（`~/.agents/docs/principles/attack-the-premise.md`）。

## [3] 契約の既定欄

- Goal に根本原因を1文で書く（どこが、何を間違えているか）。症状の場所しか書けないなら[2]に戻る。
- Allowed paths に原因の場所を入れる。症状の場所だけを手当てする契約にしない。共有コードが原因なら、それを使うほかの呼び出し元での結果も Acceptance に入れる。
- テストの順番: 修正の前に「今のコードで落ちる再現テスト」を書き、今のコードで流して落ちた出力を報告に入れてから修正する。テストと修正は同じ task commit に入る（worker は commit せず、親はレビュー合格後に1回だけ commit する）。安い局所テストが書けない場合は、Verification に元の再現手順をそのまま書き、テストを省く理由を契約に書く。
- 再現テストを書くなら、変異リストに「修正を元に戻す → 再現テストが落ちる」を必ず入れる。
- 証拠で裏付けられない「念のため」の変更は入れない。仮説が外れたら、その仮説で足した変更を戻す。

## [6] 検証

- 元の再現手順を同じ環境で流し、期待した結果になることを確かめる。
- 修正前では落ち修正後では通ることを、再現テスト（省いたなら元の再現手順の前後の出力）で確かめる。
- [2] で見つけたほかの呼び出し元でも、同じ不具合が出ないことを確かめる。

## [8] 報告

何が壊れていたか、根本原因、どう直したか、どう確かめたかを、完了報告の骨組みの2の行に入れる。
