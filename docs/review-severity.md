# レビュー指摘の重大度（P0〜P3）の基準

コードレビュー・計画レビューの共通の正本。ゲートは **P0〜P2 が0件で合格**。P3 は対応任意で、P3 のために再レビューを回さない。

## 基準

| 重大度 | 基準 |
| --- | --- |
| P0 | 致命: データの破壊・喪失、秘密の漏えい、セキュリティの穴、確実に起きる停止 |
| P1 | 重大: 通常の操作や現実的な条件で、誤った結果・データの不整合・処理の停止・契約の主要な要件の未達が起きる |
| P2 | 中: 現実的な特定の条件（失敗時・境界値・よくある誤操作・設計が想定する同時実行）で、利用者に見える誤動作・誤表示や、回復に手間のかかる状態が起きる。または、重要な処理（Acceptance の主要な振る舞い・データ・秘密・停止）を守るべきテストが、壊れた実装を検出できない |
| P3 | 軽微: 上のどれにも当たらないもの |

## P2 にしないもの（P3 にする）

- **起こりにくく、影響が中以下のもの**。起こりにくいとは、まれな条件の重なりが必要なこと（例: 同じ秒に2回・既に不正な値が保存済み・想定外の設定・細工したリクエストでしか届かない入力・今の経路では例外を投げる箇所がない）。影響が P0 相当なら、起こりにくくても P1 以上のまま。
- **文書・コメント・表記の揺れ**。ただし、読んだ人が誤った操作・判断をする内容なら P2。
- **重要度の低い処理を守るテストの穴**（表示順・文言の細部など）。自己参照検証（期待値を検査対象から導出する）は、守る処理の重要度にかかわらず P1 以上。
- **好み・一貫性の問題**。既存と著しく食い違う場合だけ P3 で指摘する。

起こりやすさは、契約・設計文書の前提で判断する（例: 複数のプロセスが同じ DB を使う設計なら、その同時実行は現実的な条件）。

## P0〜P2 の指摘に必ず書くこと

- **起きる条件**: どの操作・データ・タイミングで起きるか（具体例）と、現実に起きるかの見立て。計画レビューでは、計画どおりに実装したときに起きる問題として書く。
- **影響**: 起きたとき、誰に何が起きるか。

条件か影響が書けない指摘は P3 にする。
