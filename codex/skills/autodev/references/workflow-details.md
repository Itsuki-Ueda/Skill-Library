# ワークフロー詳細

## 重大度と合格ライン

- `P0`: 致命的。セキュリティ事故、データ破壊、確実な障害。
- `P1`: 重大。主要バグ、深刻なリグレッション。
- `P2`: 中程度。自動化を止めるべき問題。
- `P3`: 軽微。任意対応の改善。

両方のレビューで `P0`/`P1`/`P2` がゼロの場合だけ合格とする。レビュアが `pass` と書いていても `P0`/`P1`/`P2` を含む場合は、タグを正としてそのラウンドはfail扱いにする。

`P3` だけの場合は原則レビュー収束とする。P3は任意対応であり、ユーザーの明示指示がない限り、P3対応やP3確認のために再レビューを回さない。

コード変更後の差分レビューは、`light` / `full` を問わず、独立したCodexサブエージェントまたはClaude Code reviewerによるレビューを合格条件に含める。同一コンテキスト内の自己レビューは原則禁止であり、合格条件の独立レビューには数えない。ユーザーが明示的に「自己レビューでよい」と指示した場合だけ補助確認として実施できる。

`light` フローで省略できるのは計画文書、計画レビュー、実装前承認だけである。差分レビュー、検証、最終報告のレビュー証跡は省略しない。

## 計画文書

フルタスクでは次を書く。

- 目的
- 非技術者にも伝わる要約
- 対象ファイル
- 設計とトレードオフ
- 実装手順
- テスト方針。テストを追加しない場合は理由も書く
- 完了条件
- やらないこと
- リスクと戻し方

プロジェクト固有のレビュー観点（重点確認項目・検証方針）は、そのプロジェクトの `AGENTS.md` に書く（この汎用スキルには書かない）。

## CC reviewer用プロンプト

初回プランレビュー:

```text
モード=プランレビュー
対象=<absolute-plan-path>

対象の作成経緯を知らない第三者として、reviewer 定義の規律で審査してください。
P0-P3タグ、根拠箇所、具体的な壊れ方、VERDICTを必ず出してください。
```

プラン再レビュー:

```text
モード=プラン再レビュー
対象=<absolute-plan-path>
前回指摘=<findings>
修正サマリ=<summary>

対象を再読し、前回指摘への対処と修正起因の新規問題を独立に審査してください。
```

初回差分レビュー:

```text
モード=差分レビュー
対象 diff 範囲=origin/main...HEAD

対象の作成経緯を知らない第三者として、reviewer 定義の規律で審査してください。
```

差分再レビュー:

```text
モード=差分再レビュー
対象 diff 範囲=origin/main...HEAD
前回指摘=<findings>
修正サマリ=<summary>

現在の差分を再読し、前回指摘への対処と修正起因の新規問題を独立に審査してください。
```

## fallback

- CCサブスクリプションゲートウェイが失敗した場合は、生のエラーを記録し、直接`claude`へ迂回しない。
- 到達可能なClaude Codeセッションがあり、そのセッションもサブスクリプション認証だと確認できる場合だけagmsgを試す。
- agmsgも失敗した場合は、CC側の二重レビューが使えないことをユーザーへ伝える。Codex完結で続ける場合でも、コード変更後はCodex独立サブエージェントレビューを必ず行う。
- Codex独立サブエージェントも起動できない場合は、完了報告、commit、PR作成、mergeへ進まず、自己レビューもせず、停止理由をユーザーへ報告する。
- CC実装が同じ問題で2回止まる場合は、リスクに応じてCodexが引き取るかユーザーに確認する。
- 最終PRレビューが3回の再レビューでも未収束の場合は、自動mergeせずユーザーにエスカレーションする。

## Git規律

- 他者PRをレビューする前はfetch/pruneし、できるだけ新しいreview worktreeを使う。
- リポジトリ規約が別にない限り、差分baseは `origin/main` を使う。
- 古いreview worktreeを既定で再利用しない。
- merge前に `git status` がcleanであることを確認する。
