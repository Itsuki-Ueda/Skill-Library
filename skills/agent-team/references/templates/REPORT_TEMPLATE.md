# 完了報告の骨組み

[8] の最終報告と status の報告で使う。状況ページのURLは、人間への報告・質問のすべてに添える。決めるのは順番と必ず入れるものだけ。
書き方は `~/.agents/docs/writing-policy.md` に従う。

1. 1文目に、人間の判断が必要なものの件数を書く。「判断が必要なものは2件です」「判断が必要なものはありません」。次の行に状況ページのURLを置く（下の「状況ページ」）。
2. 頼まれたこと1つにつき1行で、結果を言い切る。できた・途中・失敗・未確認のどれか。何が変わったかを、人が使う言葉で書く。
3. 気をつけること（多くても3行）。人間が知らないと困ることだけ。最後に合格したコードレビューの「注意点」から選び、無ければ自分で書く。何も無ければ書かない。
4. 判断待ちを1件ずつ。推奨とその理由、答えなかったらどうなるかを付ける。
   例: 「main に統合してよいか。推奨は統合です。テストと独立レビューが済んでいます。答えが無ければブランチのまま残します」
5. 詳細は最後にまとめる。台帳の1行（[8] だけ。`close-mission.sh` の出力）、検証・レビューの達成状況、例外受入・残課題、保持している資源、ブランチ・PR・ミッションファイル。

- 1〜4の本文は、図や表を除いて400字を目安にする。
- コミットのハッシュ、ファイルのパス、テストの件数は、読む人が動くのに要るときだけ本文に書く。それ以外は5に置く。
- 件数・回数・時間は記録で数え直してから書く（原則「数字の出どころを説明する」）。数え直していない値は「自己申告」と書く。

## 状況ページ

並列のミッションの状況を、全リポジトリで1枚のページ（Artifact「ミッション状況」）に表で出す。

- Artifact の一覧から題名「ミッション状況」を探す。無ければ `templates/STATUS_PAGE.html` を capabilities `{"db": {}}` で公開して作る。リポジトリごとに作らない。
- そのリポジトリのミッションのうち、ミッションファイルの「担当:」が自分（`git config user.email`）のものだけを書く。STATE.md は全員のミッションを含むので、そのまま写さない。「担当:」の行が無い古いミッションは書く。
- 書くミッションを、ページの記録（ArtifactData）の `missions` に1行ずつ書く。doc_id は `<リポジトリのディレクトリ名>-<M-ID>`。項目は repo・mid・title（やること。人の言葉で1行）・status・waiting（人間待ちは「あなた: 〜」、無ければ「なし」）・next・updatedAt（ISO 8601）。閉じたミッションは閉じた回の報告で「完了」にし、以後は書かない。
- status は「計画中・計画の承認待ち・判断待ち・実装中・レビュー中・完了・止まっている」の7つだけ（ほかの値はページで「進行中」に入る）。
- 既にある行は先に list で version を読み、`if_version` を付けて batch の set でまとめて書く。version が合わず断られたら読み直して書き直す。
- 人間が完了の行にチェックすると `seen` に入り、ページから消える。エージェントは `seen` を消さない。チャットで「確認: M-030」と言われたときだけ `seen/<doc_id>` に書く。
- ページを使えない（Artifact や ArtifactData の道具が無い・失敗した）ときは、ページと同じ列（ミッション・やること・状態・待っているもの・次）の表を、URLの行の代わりに報告の本文に置き、ページを更新できなかったと一言書く。
