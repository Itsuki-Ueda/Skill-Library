# /agent-team — チーム開発の共通手順

## 適用範囲

agent-teamで進行中の開発は、後続の追加実装・修正・再開にも継続適用する。毎回の明示指定は不要。無関係な依頼や軽微な変更は対象外とする。

## 原則

- 現在のセッションがOrchestrator。親モデルの切替で品質条件は変えない。計画・割当・受入・状態管理を担当し、実装はworkerへ委譲する。集約ファイルの登録だけは親が担当する。
- サブエージェントは事前定義を使う。セッションごとのモデル選択やdispatchごとの設定照合は追加しない。
- 通常ミッションの計画・コードは独立レビューと別ベンダーの視点を確保する。担当の組合せはハーネス用ラッパーに従い、実装者の自己承認は禁止する。expressは `references/express.md` に従う。
- 指標はミッションの精度と完遂速度の両方。依存も競合資源も無い作業は並列で進め、直列にするのは依存か競合資源を名指しできるときだけ。
- 契約、レビュー、統合後の検証が揃うまで完了としない。現在の要件を満たす簡潔な実装を選び、既存機能を再利用する。
- 状態はファイルに保存し、上限・書込権は `references/state-layer.md` に従う。
- 人間に判断を聞いたら、答えが来るまでその判断に左右される箇所は実装・dispatchしない（推奨案での先行実装もしない。外れると丸ごと手戻りになるため）。判断に左右されない作業は続けてよい。何を止めて何を続けているかを質問に添える。ハーネスやプロジェクトの既定が「推奨で進める」でも、この規則を優先する（2026-10-18 人間の指示）。

## 読み込みと設定

1. Claude Code用ラッパー `~/.agents/claude/skills/agent-team/SKILL.md` を読む（既読なら再読不要）。共通本体が直接ロードされた場合もこの入口を使う。
   進行役はClaude Codeだけ。Codexがこのスキルを読んだ場合は使わず、通常の作業として進める（Codex用の進行経路は2026-10-17に削除。戻すときは削除前の commit 5d5b804 から復元する）。
2. 本流・resumeでは `references/defaults.yaml` と `.agents/config/team.yaml` を読む。設定の解決はラッパーに従う。
   会話の圧縮後と、別の会話で継続するときも、次のdispatch前に1回読み直す。要約や前の会話に残ったmodel・effortは使わない。
3. `.agents/state/STATE.md` → 対象ミッション → `.agents/state/MEMORY.md`。履歴全量は読まない。
4. 工程に必要な資料だけ読む: 分解・実行はdispatch、[4]〜[6]はexecute、S判定はexpress、状態操作はstate-layer、契約作成はtemplates、作業の型は[1]で選んだ型のファイル（2つ当たれば両方）。実行プロトコルは該当経路だけ読む。
   dispatchと契約の雛形は、既読でも**ミッションの[3]を始めるたびに読み直す**。手順は運用中に更新されるので、長く続く会話では古い版のまま進んでしまう（E8）。

作業ツリーに `.agents/` が無い場合は、`git log --all --oneline -- .agents` と既定ブランチの状態ファイルを調べる。
履歴にあれば敷設済みとして対象commit/PRを特定し、復元・統合を提案する。履歴にも無い場合のみinitを提案する。
Git操作は `~/.agents/skills/git-ops/SKILL.md` に従う。

## モードと規模

| 呼び出し | 動作 |
| --- | --- |
| `/agent-team {依頼}` | 前提確認・intake → S/M/L判定 |
| `/agent-team init` | `references/init.md` の敷設手順 |
| `/agent-team status` | 行数、STATE/BACKLOG/queueを読み、現状・超過を `references/templates/REPORT_TEMPLATE.md` の順番で報告するだけ。記憶整理・session記帳・commitはしない |
| `/agent-team resume` | 下記の引継ぎ手順 |

- **S / express**: 対象ファイル確定、設計判断不要、diff一読でレビュー可能。`references/express.md` へ。
- **M**: 分解不要だが契約・独立レビューが必要。1タスクで下記工程を回す。
- **L**: 依存する複数タスクへ分解し全工程を回す。
- **ミッションの単位**: 1つのPRで出せ、Acceptanceを1回の統合ゲートでまとめて確かめられる成果を1ミッションとする。目安はタスク3〜8件・依存の深さ3まで・途中で人間の判断が要らないこと（判断は[3]の承認でまとめる）。目安は台帳（[8]）で見直す仮置きの値。
  - 分ける: 別々に出荷できる成果が混ざる／8件超または依存の深さ4以上／前提をスパイクで確かめる必要がある（スパイクを先のミッションに）／途中で人間の判断が要る（判断の地点で区切る）／共有基盤の変更とそれを使う機能が同居する（基盤を先に）。分けたミッションは[1]の並走提案に乗せる。
  - まとめる: 同じ領域で1タスクのMが続く、またはBACKLOGに同じ領域の小さな項目が並ぶときは、1ミッションにまとめることを人間に提案する（計画承認・executor起動の固定費を1回にする）。
- 規模判定に迷ったら人間に確認する。

## ミッションフロー

各工程の完了条件を満たしてから次へ進む。未達はミッションとSTATEのBlockersに記録する。

### [0] 前提確認
- 設定と状態を読み、`bash ~/.agents/skills/memory-ops/scripts/check-size.sh` で計測する。
- 閾値超過は `~/.agents/skills/memory-ops/SKILL.md` に従い整理する。閾値+10%未満のみ[7]へ先送り可。statusは報告のみ。
- 閉じたのに台帳に無いミッションを記録する: `python ~/.agents/skills/agent-team/scripts/mission_cost.py <リポジトリ> --missing`（[8]の付け忘れの受け皿。2026-10-06〜09に12件が未記録だった）。
- 完了条件: 必須設定・状態が読め、上限内または許容された先送りである。

### [1] Intake
- 依頼が作業の型に当たるなら、その型を読む: 不具合修正 `references/types/bug-fix.md` / 機能追加 `feature.md` / リファクタ `refactor.md` / 性能 `perf.md` / 比較評価（方式・モデル等を比べて人間が選ぶ） `comparison.md` / 画面 `ui.md`（いずれも `references/types/`）。型は、自分の見出しにある段の中身を決める。見出しの無い段は本体どおり。2つに当たる（画面を含む機能追加など）なら両方を読む。当たらない依頼は型なしで進める。選んだ型はミッションの `型:` に書く（executor はここを見て型の[6]を完了ゲートに入れる）。
- `bash ~/.agents/skills/explain-page/scripts/list.sh <リポジトリ> 設計判断` で過去の設計判断を見て、依頼に関係する決定があればミッションの制約に `E-xxx` 付きで書く。決定と食い違う依頼なら、進める前に人間に確かめる。 判断待ち（`Status: open`）の記録があれば、explain-page の「判断待ちを閉じる」に従い、Intake の確認と一緒に人間に聞いて閉じる。
- Goal、検証可能なAcceptance、制約、Human Escalationを確定する。不明点だけ人間に確認する。「ミッションの単位」に照らして分ける・まとめるべきなら、ここで人間に提案する。
- `references/templates/MISSION_TEMPLATE.md` からM-xxxを採番し、STATEに索引を追加する。
- ブランチはgit-opsの命名に従う（例: `feat/m-xxx-summary`）。
- STATEに他のactiveミッション、またはBACKLOGに着手可能な独立項目があれば、別のセッション・worktreeで同時に進めることを人間に提案する。触るファイル・DB・ポート等が重なるものは直列と明記する。並走中の各セッションは自分のミッションのファイルとSTATEの自分の索引行だけを書く。
- 完了条件: 成功条件と作業範囲を文書化した。

### [2] 調査（必要時）
- 調査担当へ `~/.agents/skills/team-researcher/SKILL.md`、質問・範囲・除外範囲を渡す。型があれば型の「調査の問い」を質問に入れる。
- 独立した調査は並列化できる。重要領域の意図的な重複で矛盾を検出する。報告の採用規律はdispatchを参照。
- 読み取り専用担当の結果は親が `queue/research/` に保存する。
- 誤っていると計画全体を覆す前提は、権限内の小さな実験で検証する（根拠E1）。
- 完了条件: 判断に使う主張に根拠がある。

### [3] 分解・計画レビュー
- Goal / Acceptance / Allowed paths / 依存 / 実装者を骨子にする。型があれば型の「契約の既定欄」を入れる。契約はdispatch前に `GENERAL_TEMPLATE.md` へ清書する。委任されたexecutorがいれば清書を任せる。
- テストを書く契約では、骨子段階から変異リストを作る。**どのファイルのどの箇所を何に変えるか**を特定し、機構の削除・置換では維持すべき挙動の変異も列挙する（E2）。CI・デプロイ・戻し（復旧）の仕組みも変異の対象にする。例: 戻し先を今と同じ版にしても「戻し成功」と出ないか（2026-10-19 振り返り。戻しの検証が誤実装でも通る形だと計画レビューで2回指摘された）。
- Acceptanceに登場するデータ・状態・設定値の生産者/消費者表を埋める。空欄ならdispatchしない。表の効果は数ミッション後に件数で点検する（E3）。
- `references/dispatch.md` で担当を選び、依存とAllowed pathsからステップ（同時に起動できるタスクの組）を組む。**Allowed pathsが交差しなくても、検証が他タスクのパスを読み込むなら作業ツリーは競合資源**であり、レーンをworktreeで分ける（dispatch「並列実行の規律」）。直列化は競合資源を名指しする。集約ファイルは親の担当とする。
- レーンを分ける場合は、レーンごとの担当ファイル群・ブランチ・worktree・進行管理者をミッションの並列計画に書く。合流の順序と、合流後の再検証も計画に含める。
- 別ベンダーの独立担当へ `~/.agents/skills/team-plan-reviewer/SKILL.md` と分解文書を渡す。初回はplan-probeも並走させる。
- probeには `~/.agents/skills/team-plan-probe/SKILL.md` と文書パスだけを渡す。ズレは**曖昧箇所の候補**。読み落としか原文の不足か確認し、初回修正へまとめる。probeは合否に数えない。
- レビューの合格・版記録・再レビューはdispatchに従う。上限は `limits.fix_rounds_plan`。
- 指摘を直すときに新しい仕組み（手順・判定方法・設定値・データの形）や、テスト・受入条件・案内文を足すなら、書く前にその前提（使う道具・ライブラリの実際の動き、既存のコード、既存のテスト、既存の決定、計画の他の節）をコードか公式資料で確かめ、出典を対処記録に書く。[2]の調査と同じ扱いにする（2026-10-20 に12リポジトリの記録を調べた結果。P2だけの回を直したあとの再レビューで出たP1は6件で、6件とも直しで足した仕組みが確かめていない前提に乗っていた。うち4件はコードか公式資料を一度読めば分かった。2026-10-21 に過去30件で試すと、直しで生まれた前提ずれの指摘24件のうち11件を書く時点で見つけ、P1は4件中3件を見つけた。誤った指摘は約40件中3件だった）。
- 計画の再レビューは、P0・P1が出たとき、または直しで新しい仕組みを足したときに行う。P2以下だけで、直しが文言の修正・矛盾の解消・テストや条件の追加にとどまるなら、再レビューせず対処を記録して合格とする（dispatchの「合格はP0〜P2ゼロ」より優先。計画レビューだけに当てはめ、コードレビューは従来どおり）。
- 指摘の由来を「修正起因／以前から存在」で区別する。修正起因が過半なら分解を見直す。上限超過時は文書の矛盾／実験が必要／上流設計の判断に分類し、再分解・スパイク・gpt-consult等の選択肢を人間に提示する（E1）。
- 分解と並列計画は人間の承認を1回得る。既存の承認範囲内で同じ確認を繰り返さない。
- 分解後にタスクが8件を超える、または依存の列が4段以上になったら、ミッションを分けることを承認時に人間へ提案する。
- 完了条件: 契約・計画レビュー・承認と並列計画（ステップ数・依存の深さ・直列にした箇所の理由）が揃った。

### [3.5] 進行管理の委譲（該当時）
- ラッパーに定義された節約運用が該当する場合のみexecutorへ[4]〜[6]を委任する。
- 委任はミッションとqueueへの記帳に限定する。STATEの縮約、人間の判断、破壊的操作の判断は親に残す。委任先が使えなければ親が進行管理する。
- この委任は実装者の変更やレビュー条件の緩和を意味しない。

### [4]〜[6] 実行・レビュー・統合
- 手順は `references/execute.md`。executorへ委任したら親は読まない（executorが読む）。親が直接進行管理するときだけ読む。
- 親が受け取るときの完了条件: 全タスクの報告・最終版に紐づく合格・検証証拠・画面確認の記録（該当時）・型の[6]検証の記録（該当時）・task commit、統合後HEADでの `verify.post_change` / `verify.smoke` の実行記録、変異証拠が揃った。

### [7] 受入・状態整理
- Acceptanceと証拠を照合する。フロントエンドは実描画を確認する。親の差分確認は要件に直結する範囲を抜き取り、独立レビュー全量を機械的に繰り返さない。
- 必須レビュー未達はdispatchの縮退規則に従い、通常のdoneにしない。
- 戻し（復旧）の受入では、戻した版が戻す前の版と別物であることを実行記録の版（SHA 等）で照らし合わせる。「戻し成功」の表示だけで受け入れない（2026-10-19 振り返り）。
- 見送ったP3でも、人間の要望を満たさない穴を残すものは、最終報告の「例外受入・残課題」に必ず載せる。「例外受入なし」と書かない（2026-10-19 振り返り。要望に穴を残すP3を見送り、例外受入を「なし」と書いた）。
- 別の作業を理由に先送りした項目は、閉じる前にその理由がまだ残っているか確かめる。解けていれば今回で片付けるか、BACKLOGに積み直す。
- 人間の指摘・エスカレーション・NEED-DECISION があったミッションと、同じレビュー（同じ計画・同じタスク）の修正が上限（`limits.fix_rounds_*`）に達したミッション（上限内の最後のレビューまで進んだ。合否は問わない）では、ミッションを閉じる前に `~/.agents/skills/reflect/SKILL.md` で振り返り、採用・却下・保留の表をミッションファイルに書く（閉じる処理と状態commitに含めるため）。採用案の反映は人間の承認を待つので、[8]の最終報告の判断待ちに「改善案 N 件の反映」として1件で載せ、表のあるミッションファイルのパスを添える。上限より前に合格したものだけなら振り返らない（2026-10-18 人間の決定、2026-10-21 に「2回続けて不合格」から「上限に達した」へ変更。振り返りが頻発していたため。振り返りは1回で数分と数ドルかかり、上限前の不合格はレビューの差し戻しで既に直っているため）。
- state-layerに従いSTATEのLogを1行に縮約し、sessionをクリアしてから、ミッションを `bash ~/.agents/skills/agent-team/scripts/close-mission.sh <M-ID> [<作業場所>]` で閉じる（closedへの移動・撮影画像の掃除・台帳への記録を1回で行う。記録ファイルを手で移さない）。教訓はmemory-opsの入口に従う。
- 行数を再計測し、必要な整理と状態commitを終える。PR希望時はミッション単位で作成し、作成の直前に git-ops を読んでブランチ・タイトル・本文をその§1・§2に合わせる。
- 完了条件: 受入証拠と引継ぎ可能な状態が揃った。

### [8] Closeout・最終報告
- git-opsに従いミッション由来の一時worktree・統合済みブランチを後片付けする。
- 未統合・ロック等で保持する場合は理由と次の削除条件を記録する。未処理を黙って放置しない。
- 費用と品質の記録（ローカル台帳 `~/.claude/agent-team-ledger.jsonl`）と撮影画像の掃除は、[7]の `close-mission.sh` が済ませている。その出力の1行を最終報告に載せる。改善の効果はこの台帳で前後比較する。台帳には作業時間（人間の待ちを除く）・ステップ数・依存の深さ・executorの代数も載るので、精度と完遂速度の両方で比べる。
- 最終報告は `references/templates/REPORT_TEMPLATE.md` の順番で書く（1文目は判断待ちの件数。変更・検証・レビュー達成状況・例外受入・残課題・保持資源は末尾の詳細に置く）。件数・回数・時間は記録で数え直してから書き、数え直していない値は「自己申告」と書く。
- 完了条件: `close-mission.sh` の出力の1行（台帳の記録）と、後片付けの結果を載せた最終報告を出した。

## init
`references/init.md` の手順で敷設する。

## resume
1. STATEと対象ミッションを読む。複数activeなら対象を確認する。
2. 他sessionのActive sessionが残る場合は二重運転を警告し、人間が引継ぎ可否を判断するまで記帳・整理しない。
3. 上限を計測・整理し、自sessionを記録する。Tasks/Next actionsから再開する。
4. 未回収の担当は記録したsession・報告・ラッパーの継続手段で確認する。未回収を完了扱いにしない。

## 禁則・参照
- 契約なしのdispatch、workerによるgovernance編集、権限回避、未実行の合格報告（原則「本物で確かめる」）は禁止。
- workerのgovernance禁止には `.agents/`、AGENTS.md、CLAUDE.md、ハーネス設定を含む。報告・調査結果の保存は親が代行する。
- 通常ミッションの独立レビューをexpressの例外で省略しない。
- 規則の実測背景は `references/evidence.md`（必要時のみ）。状態の詳細はstate-layer、実行共通規律はdispatchを参照。
