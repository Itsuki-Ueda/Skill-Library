# 作業の型: リファクタ

途中で欠けている機能や不具合が見つかったら、別のミッションに分け、構造の変更を先に出す。
この型は、自分の見出しにある段の中身を決める。見出しの無い段は共通本体どおりに進める。

## [2] 調査の問い

1. 今の振る舞いは何か。それを固定する方法（今の出力を記録したテスト、スナップショット、新旧の出力を比べるスクリプト）は何か。型チェックと lint は振る舞いの固定にならない。
2. コードに欠けている形は何か。今作るなら、モジュールの分け方・型・呼び出しの関係はどうなるか。
3. 先に消せるもの（使われていないコード、呼び出し元が1つの包み、重複した検査、孤立した参照）は何か。
4. 変える API の呼び出し元はすべてどこか（文字列・文書・コメントの中の参照も含む）。

## [3] 契約の既定欄

- 作り替えの前に「今の振る舞いを固定するテスト」を書き、今のコードで流して通った出力を報告に入れてから構造を動かす。固定テストと作り替えは1つのタスクにし、固定そのものが大きいとき（土台から作る・複数のモジュールにまたがる）だけ分ける。
- 順番は、消す、作り替える、後片付け。どのコミットでも固定したテストが通る。
- API を変えるなら、同じミッションの中で呼び出し元をすべて移し、古い API を消す。互換のための包みや、新旧の並走は作らない（外部の利用者がいるなら例外にし、契約にそう書く）。
- 形を足すなら、分岐・重複した決まり・ありえない状態のどれが減るかを Goal に書く。どれも減らないなら作り替えない。
- 名前を変えるなら、文字列・文書・コメントの中の参照も Acceptance に入れる。

## [6] 検証

- 固定した振る舞いが変わっていないことを、[2] の1で決めた方法で実物で確かめる。
- 読み手の負担が減ったかを確かめる（層、隠れた状態、分岐の数）。どこでも減っていない変更は戻す。

## [8] 報告

変えた構造、固定に使ったもの、変わっていないことの証拠、減った負担を、完了報告の骨組みの2に入れる。
