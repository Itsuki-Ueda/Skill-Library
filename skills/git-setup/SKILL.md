# git-setup — Git初期セットアップの正本

このスキルは、**リポジトリの人生で一度しか実行しない工程**（作る／持ってくる）の手順の正本である。
ここを雑にやると、後から直すのが高コストな問題（秘密情報のコミット、改行コード事故、
ブランチ名の不統一、author の取り違え）がリポジトリの履歴に焼き付く。だから手順を固定化する。

## 0. git-ops との境界（どちらを読むか）

| やること | 読むスキル |
|---|---|
| リポジトリを作る／クローンして開発できる状態にする（**一度きり**） | **このスキル** |
| ブランチを切る・PRを出す・マージする・worktree・後片付け（**毎日**） | `git-ops`（`~/.agents/skills/git-ops/SKILL.md`） |

初期セットアップが終わった瞬間から、以降の操作はすべて `git-ops` の管轄。
**このスキルに日常運用のルールを書き足さない**（二重管理になるため）。

## 1. 着手前チェック（全シナリオ共通・省略禁止）

作る前でも持ってくる前でも、**まずここを確認する**。順番に意味がある。

### 1-1. 【必須ゲート】どのアカウントで作業するかを確定させる

**このゲートを通過するまで、`git commit` / `git push` / `gh repo create` を実行しない。**

> **なぜゲートにするのか**: author（コミットの名義）は**後から直せない**。履歴の書き換えが必要になり、
> push 済みなら実質不可能。私用リポジトリに仕事用アドレスでコミットすると、公開リポジトリでは
> 消せない形でメールアドレスが残る。「表示された既定値をそのまま使う」を許すと、この事故が素通りする。

#### 手順1: 現在の状態を取得する（判断材料の収集であって、判断そのものではない）

```bash
git config --global user.name && git config --global user.email
gh auth status
```

#### 手順2: 対象リポジトリの owner からアカウントを機械的に判定する

| リポジトリの owner | 使うアカウント | 人への確認 |
|---|---|---|
| **仕事用 org**（会社の GitHub Organization） | 仕事用（`itsukiueda-ourai`） | **不要**（既定と一致するため） |
| **個人アカウント**（`Itsuki-Ueda` 等） | 私用（`Itsuki-Ueda`） | **不要**（`Documents/個人開発/` 配下に置く場合。手順4へ） |
| **判定できない / owner 未確定**（新規作成でどこに作るか未決 等） | — | **必要**（手順3へ。推測で進めない） |

クローンの場合は owner が URL から確定するので、多くはここで判定が終わる:

```bash
git remote get-url origin      # クローン後
```

#### 手順3: 判定できないときは**人に確認してから**進む（fail-closed）

以下を提示して選ばせる。**黙って既定値で進めない。**

- 使うアカウント（仕事用 `itsukiueda-ourai` / 私用 `Itsuki-Ueda`）
- 新規作成なら、リポジトリの owner（どの org / 個人アカウントの配下に作るか）

> 迷ったら止めて聞く。ここで1回聞くコストは、間違った名義のコミットを取り消すコストより桁違いに小さい。

#### 手順4: 私用と決まったら、**置き場所で解決する**（設定を書かない）

author はディレクトリで自動的に決まる（`~/.gitconfig` の `includeIf`）。
**私用リポジトリは `Documents/個人開発/` 配下に置く。それだけで私用名義になる。**

この外に置かざるを得ないときだけ、そのリポジトリの中で上書きする:

```bash
git config user.name "Itsuki-Ueda"
git config user.email "73779819+Itsuki-Ueda@users.noreply.github.com"
```

`--global` を付けなければ、そのリポジトリ限定の設定（`.git/config`）になる。
**グローバル設定は変えない**（自動切替の前提が崩れ、以降の名義が全部ずれる）。
値の正本と仕組みは `~/.agents/AGENTS.md` の「Git author 設定」節。**ここには値を複製しない。**

#### 手順5: 初回コミット直前に**実効値**で最終確認する

```bash
git config user.name && git config user.email      # ← --global を付けない
```

`--global` を付けずに実行すると、**そのリポジトリで実際に使われる値**が返る
（リポジトリ単位の設定があればそれが優先され、なければグローバルの値が返る）。
コミットに刻まれるのはこの値。**手順2で判定したアカウントと一致していなければ、コミットしない。**

### 1-2. GitHub CLI のアクティブアカウントを author に合わせる

```bash
gh auth status
```

`Active account: true` が付いているアカウントで push・リポジトリ作成が行われる。
**author（誰がコミットしたか）と push 先の認証（誰が送ったか）は別物**なので、両方が意図どおりか見る。
ズレていると「仕事用名義のコミットを私用アカウントで push」のような混線が起きる。

§1-1 で確定したアカウントと違う場合は切り替える:

```bash
gh auth switch --user <account>
```

> **これは共有状態の変更**（このマシンの他の作業にも影響する）。切り替えたら、作業終了後に
> 元のアカウントへ戻す。既定の状態は仕事用（`itsukiueda-ourai`）。

#### private な個人リポジトリは、切替に頼らず**リポジトリ単位で認証を固定する**

gh の credential helper は**アクティブアカウントのトークンしか返さない**。よって仕事用が
アクティブだと、private な個人リポジトリへの `push`/`fetch` が `Repository not found` で失敗する。
毎回切り替えるのは戻し忘れ事故の元なので、そのリポジトリの local config で固定する:

```bash
git config --local --add 'credential.https://github.com.helper' ''
git config --local --add 'credential.https://github.com.helper' '!f() { test "$1" = get && { echo username=Itsuki-Ueda; echo "password=$(gh auth token --user Itsuki-Ueda)"; }; }; f'
```

1行目の空リセットは、継承される gh の helper を打ち消すために必須。
トークンは keyring から都度取得するので**平文でディスクに置かれない**し、更新にも自動追従する。
確認は `git ls-remote origin`（アクティブが仕事用のまま成功すれば正しい）。

> 🚫 **リモートURLにトークンを埋め込まない**（`https://user:gho_xxx@github.com/...`）。
> `.git/config` に平文で残り、`git remote -v` やログに漏れる。
> 2026-09-07 に1件実害があり、除去して上記 helper に置換した。
> 認証が切れたら helper を直す。URL にトークンを戻さない。

gh CLI（`gh pr` 等）は per-repo 設定が無いので、切替せず1コマンドに閉じる:
`GH_TOKEN=$(gh auth token --user Itsuki-Ueda) gh pr ...`

### 1-3. デフォルトブランチ名

このマシンは `init.defaultBranch` が**未設定**（＝ `git init` すると `master` になる）。
グローバル設定の変更は影響範囲が広いので勝手に変えず、**コマンド側で毎回 `main` を指定する**:

```bash
git init -b main
```

### 1-4. 改行コード（Windows 固有の地雷）

このマシンは `core.autocrlf` が**未設定**。
マシン設定に頼るとメンバー間で挙動がズレるので、**リポジトリに `.gitattributes` を置いて明示する**（§2-2）。

> **なぜ問題になるのか**: Windows は改行を CRLF、Linux/Mac は LF で表す。混ざると
> 「1文字も編集していないのに全行が差分として出る」状態になる。さらに husky の Git フックは
> シェルスクリプトなので、CRLF が混入すると**実行できずフックが黙って壊れる**。

## 2. シナリオA — ゼロから新規リポジトリを作る

### 2-1. ローカルに作る

```bash
mkdir <project> && cd <project>
git init -b main
```

### 2-2. `.gitignore` と `.gitattributes` を**最初のコミットの前に**置く

順番が重要。先にコミットしてしまうと、無視したかったファイルが履歴に残る
（後から `.gitignore` に足しても、**すでに入ったものは消えない**）。

`.gitattributes`（テンプレート。プロジェクトに応じて調整）:

```gitattributes
# リポジトリ内は常に LF で保存し、チェックアウトも LF に揃える
* text=auto eol=lf

# Windows 専用スクリプトだけは CRLF でないと動かない
*.bat  text eol=crlf
*.cmd  text eol=crlf
*.ps1  text eol=crlf

# バイナリは変換対象外にする（壊れるため）
*.png  binary
*.jpg  binary
*.pdf  binary
*.xlsx binary
```

`.gitignore` に**必ず**含めるもの:

```gitignore
node_modules
dist
.env
.env*.local
.vercel
```

### 2-3. 初回コミット前の秘密情報チェック（最重要）

空リポジトリの初回コミット・初回pushのみ、既定ブランチへの直接作成を許す。既存リポジトリへのagent-team敷設は初回コミットの例外に含めず、git-opsに従う専用PRで先に統合する。

```bash
git add -A
git status --short          # これから履歴に入るファイルの全リスト
```

このリストを**目で見て**、`.env` / 鍵ファイル / 認証情報が含まれていないことを確認する。

> **なぜ必須か**: 一度 push した秘密情報は、後からファイルを消しても**履歴に残り続ける**。
> GitHub にプッシュされた時点で「漏洩した」とみなして鍵の再発行が必要になる。
> `git status` を1回見るコストのほうが圧倒的に安い。

問題なければコミットする（メッセージは Conventional Commits ＝ `git-ops` の規約）:

```bash
git commit -m "chore: initial commit"
```

### 2-4. GitHub にリポジトリを作成して push

**この操作は外向き・取り消しにくいので、実行前に必ず人間の承認を得る。**

```bash
gh repo create <owner>/<repo> --private --source=. --remote=origin --push
```

- **`<owner>/` を省略しない。** 省略すると認証中の**個人アカウント配下**に作られる。
  組織のリポジトリのつもりが個人に出来る事故はこれが原因。
- `--private` / `--public` は明示する（どちらかが必須）。**公開は不可逆に近い**ので既定は `--private`。
- `--source=.` は「今いるローカルリポジトリを中身として使う」指定。`--push` で初回 push まで行う。

### 2-5. リポジトリ側の設定

`delete_branch_on_merge` / `main` のブランチ保護 / スカッシュマージ限定は
**`git-ops` §5 が正本**。そちらのコマンドを使う（ここには複製しない）。

初期セットアップは、この設定を入れる**唯一の自然なタイミング**。後回しにすると、
保護のない `main` に直接 push される事故が起きてから気づくことになる。適用には人間の承認が必要。

## 3. シナリオB — 既存リポジトリをクローンして開発できる状態にする

「開発できる状態」とは、**ビルドが通り、開発サーバーが起動するところまで確認済み**を指す。
クローンしただけ・`npm install` しただけで完了と報告しない。

### 3-1. クローンと素性の確認

```bash
git clone https://github.com/<owner>/<repo>.git <dir>
cd <dir>
git log --oneline -3      # どの時点のコードか
git branch -a             # 作業対象のブランチが存在するか
git status --short        # ← 空であること
```

> `git status` がクローン直後に差分を出す場合、**改行コードか `.gitattributes` の問題**を疑う（§1-4）。
> 「とりあえず commit」で潰してはいけない。全行差分の PR が生まれる。

### 3-2. セットアップ手順の**出典を先に読む**

推測でコマンドを叩かない。この順で探す:

1. `README.md`
2. `docs/` 配下（`*deploy*` `*setup*` `*development*` 等）
3. `package.json` の `scripts`（実際に存在するコマンドの一次情報）

### 3-3. 依存インストール

```bash
npm install       # ロックファイルの種類で pnpm / yarn を使い分ける
```

### 3-4. 環境変数の準備

```bash
# 必要な変数名を、コードから機械的に洗い出す
grep -rEo '(process\.env|import\.meta\.env)\.[A-Z_0-9]+' --include='*.ts' --include='*.tsx' .
```

- `.env.example` があればコピーして使う。無ければ、上で洗い出した変数名でテンプレートを作る。
- **秘密の値を推測で埋めない・勝手に既存の鍵を流用しない。** 空欄にして人間に依頼する
  （API キーの取り扱いは `~/.agents/AGENTS.md` の規定に従う）。
- 作ったファイルが `.gitignore` の対象に入っていることを確認する:

  ```bash
  git check-ignore -v .env.local     # 何も出なければ「無視されていない」＝危険
  ```

- **本番用の値をローカルにそのまま入れない。** ローカルでは動かない設定が混ざる
  （例: cookie のドメイン指定は `localhost` では機能しない）。コード内のコメントや
  設定ファイルにローカル用の指定方法が書かれていないか確認する。

### 3-5. 疎通確認（ここまでやって「完了」）

```bash
npm run build     # ビルドが通るか
npm run dev       # 開発サーバーが起動し、実際に応答するか
```

起動しっぱなしにせず、**確認したら停止し、ポートが解放されたことまで確かめる**。

秘密情報がクライアント側に漏れていないかも確認する:

```bash
grep -r "<秘密鍵の先頭数文字>" dist/ && echo "!! バンドルに混入" || echo "OK"
```

> **なぜ必要か**: フロントエンドのビルドでは、特定の接頭辞（Vite なら `VITE_`）が付いた変数だけが
> ブラウザ向けコードに埋め込まれる。サーバー専用のはずの鍵が誤って接頭辞付きで定義されていると、
> **ビルド成果物として全世界に配布される**。ローカルで一度確認すれば防げる。

### 3-6. 未確認事項を正直に申告する

外部サービスへの実接続（ログイン等）、課金が発生する API 呼び出し、対話が必要なコマンドは、
確認できないなら**確認できていないと明記する**。「たぶん動く」を「動作確認済み」と報告しない。

## 4. やってはいけない（実際に起きる事故）

- **アカウントを確定させずにコミットする** → 表示された既定値のまま私用リポジトリに仕事用名義で
  コミットしてしまう。author は後から直せない。判定できないなら**必ず聞く**（§1-1）
- **`.env` を含んだまま初回コミットする** → 履歴に残り、鍵の再発行が必要になる（§2-3）
- **`gh repo create` を `<owner>/` 省略で叩く** → 組織のつもりが個人アカウントに出来る（§2-4）
- **私用作業のためにグローバル author を変えて、戻し忘れる** → 以降の仕事用コミットが全部私用名義（§1-1）
- **`git init` を素で叩く** → `master` ブランチができ、`main` 前提の設定と噛み合わない（§1-3）
- **クローン直後の全行差分を commit で潰す** → 改行コード問題を履歴に埋め込む（§3-1）
- **`npm install` が通った時点で「環境構築完了」と報告する** → ビルド・起動確認が未了（§3-5）
- **セットアップ直後に `main` で直接作業を始める** → 以降は `git-ops` §0 の管轄。ブランチを切る
