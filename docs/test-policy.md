# テスト方針の正本（全プロジェクト共通の既定値）

プラン作成・実装・レビューの全役割が従う、テストの書き方/書かせ方の正本。

**優先順位**: プロジェクトにテスト方針の正本（`tests/README.md` 等）がある場合は**そちらが優先**
（信頼境界＝何を最優先で守るべきかはプロジェクトしか知らない）。この文書はそれが無い場合の既定値。

## 原則1: 古典派 — 振る舞いを検証する

- 検証するのは「**何をするか**」（入力に対する出力・外から観測できる状態変化）。
  「どうやるか」（内部実装・メソッド呼び出し）ではない。
- 内部の協調オブジェクトに対する `toHaveBeenCalledWith` や呼び出し回数の検証をしない。
- モック/スタブは**プロセス外依存**（DB・外部 API・時刻・乱数）の置き換えに限る。
  内部部品までモック化しない（ロンドン派への転落）。
- **テストが保証すると主張する対象そのものをモックしない**。
  例: 学習処理の性質を検証するテストで学習関数（`lgb.train` 等）をモックすると、
  テストは「モックに渡した値をモックから読み返す」だけの恒真になる。

## 原則2: 二重保証の禁止

- 集約（ハンドラ / ユースケース）のテストが既に証明した観測を、依存部品のテストで再検証しない。
- 依存部品にテストを書くなら、**その部品固有の契約**（境界値・丸め・不変条件）に限る。

## 原則3: カバレッジを追わない

- テストは**信頼境界と複雑なロジックの回帰検知**のために書く。カバレッジは数値目標にしない。
- テストする: 非自明な純関数 / 認証・認可・データ分離などの信頼境界 / 同型ハンドラ群のパターン代表 1 本。
- テストしない: 薄い CRUD の網羅 / フレームワーク自体の動作 / 「何を保証するのか」を一言で言えないテスト。

## 原則4: リファクタ中にテストが壊れたら

- 直す前に問う: 「**振る舞いが壊れたのか、テストが実装詳細を掴んでいたのか**」。
- 後者ならテストを観測可能な結果の検証に書き直す。
  **モックを足して目先のテストを通すのは禁止**（不確実性の排除と引き換えに振る舞い検証が骨抜きになる）。

## 原則5: テストケースの設計と量産の分離

- どこで何を保証するか（テストケース設計）は**プラン/仕様の段階で列挙**し、レビューと人間承認を通す。
- 実装者は**列挙されたテストだけ**書く。「ついでにテスト追加」をしない
  （提案があれば報告に書くにとどめる）。

## 原則6: 検出力 — テストの価値は「落ちること」で証明する

- テストの存在価値は「実装が壊れたとき赤くなる」こと。**一度も落ちる姿を確認していない
  テストは、保証ではなく飾り**。
- ガード（検証・例外送出・assert）を書いたら、**それを無効化するか違反入力を与えて、
  テストが実際に落ちることを確認**してから完了とする（変異スモーク。手順は付録）。
- 契約・仕様に変異リストがある場合、列挙された変異の実施は**必須**。
  実施証跡（変異内容 → 落ちたテスト名とメッセージ）なしの「確認済み」報告は無効。
- 根拠となる実測: 契約に列挙された変異は 11/11 検出、列挙されなかった変異は 15/17 が
  素通りした（keiba M-011/M-012 の変異テスト監査、2026-07）。書かれた分だけが守られる。

## 原則7: 期待値の独立性 — 自己参照検証の禁止

検証の期待値を**検査対象から導出してはならない**。期待値の源は
「契約・仕様の定数」「テスト側で固定した値」「呼び出し側の引数」のいずれかに限る。

禁止形（いずれも実際に発生した恒真検証のパターン）:

1. **検査対象データから期待値を計算する**
   （例: `expected_year = int(row_years[0])` — 全行が同じ誤りなら素通りする。
   混在データは弾けても「まるごと間違ったデータ」を弾けない）。
2. **正解値で上書きした後に等号検証する**
   （検証対象を検証直前に正しい値で書き換えていれば、検証は失敗し得ない）。
3. **検証対象と同じ関数・同じ経路で期待値を再計算して突き合わせる**
   （実装のバグが期待値側にも同じように現れるため、差分が出ない）。

レビュー時の自問: 「**この検証に、まるごと間違ったデータを渡しても落ちるか？**」。
落ちないなら、その検証は何も保証していない。

## 原則8: ガード1つに反例テスト1つ

- 拒否・例外送出のガードには、**実際に違反する入力を与えて拒否されることを確かめる
  テスト（反例テスト）を必ず対にする**。正常系が通ることだけ確認したガードは未検証。
- 反例は2種類用意する: (a) 境界が混在した入力 (b) **まるごと違反した入力**
  （(a)だけだと原則7-1型の自己参照検証が素通りする）。
- **構造的に発火し得ないガード**（正常系のどの経路でも到達しない検証・上流で同じ条件が
  先に拒否される検証）は、テストで守るのではなく**削除を指摘**する。
  死んだ防壁は「守られている」という誤った安心感を与える分、無いより悪い。
- docstring・コメントで**実装が強制していない保証を主張しない**
  （「outer ラベルへの経路を持たない」と書きながら outer ラベル列を必須要求する等）。
  主張と実装の乖離はレビューで削除・修正を指摘する。

## 原則9: fixture の自己完結

- テストの種データ（fixture）を**本番の成果物・稼働中のステータスファイルからコピーしない**。
  テスト内で合成する。
- 理由: 本番結果を fixture にすると、本番側が更新された瞬間に「レビュー時は検出力があった
  テストが、何でも通すテスト」へ**静かに退行**する。CI は緑のまま検出力だけが死ぬ
  （実例: 本番 status.json を種にしたテストが、本走結果のコミットで DETECTED→SURVIVED に退行）。
- 本番データの形を再現したい場合は、必要な最小構造をテスト内に書き下ろす。

## 原則10: 検証の粒度 — 「何かを確認した」と「契約を確認した」を区別する

- **例外テストは理由まで特定する**: `pytest.raises(SomeError)` の型照合だけでは、
  別の理由で落ちても合格する。`pytest.raises(..., match="...")` でメッセージ（＝拒否理由）
  まで照合する。
- **契約定数はテストが値そのもので断定する**: 統計契約（例: B=10,000 / seed=42）が
  実装の「既定値」にすぎないなら、呼び出し側が上書きした瞬間に契約は消える。
  テストは既定値に頼らず、契約値が実際に使われたことを値で検証する
  （テスト自身が別の値を渡して通しているなら、それは契約のテストではない）。
- **生成した検証材料は照合されて初めて保証になる**: ハッシュ・manifest・チェックサムを
  「生成するだけ」で一度も照合しない実装は、原則8の死んだ防壁と同類。
  改ざんを検出する経路（生成→保存→読込→照合→不一致で停止）を反例テストで通す。
- **状態判定は中身で行う**: 「ファイルが存在する＝完了」のような存在チェックだけの
  再開判定は、空ファイル・別実行の成果物を「完了」と誤認する。識別子（年・ハッシュ等）の
  照合まで検証する。

## 原則11: 継ぎ目は実経路で通す

- システム内部のファイル往復（書き出し→読み戻し）・シリアライズ・CLI/プロセス結合は
  **モックやメモリ上の突き合わせで代替せず、実際に往復させる**。
  継ぎ目でしか起きない不具合（浮動小数の書式落ち・型の丸め・エンコーディング）は、
  実経路を通さない限り永久に見逃す（実例: メモリ上のハッシュ照合だけを検証していたため、
  CSV 書き出しの精度落ちが本走まで発覚せず全 fold 停止）。
- **改ざん検出テストはディスク上の実ファイルを改ざんする**。メモリ上の変数書き換えでは
  読込経路の検証にならない。
- **正常系の結合を最低1本通す**。異常系（拒否・停止）だけをテストし、
  正常系（predict→evaluate が実際に繋がる）をどのテストも通していない構成を許さない。
- 原則1の「モックはプロセス外依存に限る」の明確化: 自システムが書いて自システムが読む
  ファイルは**プロセス外依存ではなく継ぎ目**であり、モック対象ではない。

## AI 量産テストの検出パターン（レビュー用）

以下に該当するテストは**削除を指摘**する。少数の鋭いテスト > 網羅的で壊れやすい群れ。

1. 別の層で既に証明済みの事実の**再証明**（原則2違反）。
2. 現在の実装を固定化する検証（呼び出し回数・内部引数の形）（原則1違反）。
3. 保証対象を一言で言えない「カバレッジのための」テスト（原則3違反）。
4. テストを通すこと自体を目的としたモック化（原則4違反）。
5. **期待値を検査対象から導出している検証**（原則7違反）— 削除ではなく独立な期待値への修正を指摘。
6. **反例テストを持たないガード**・構造的に発火不能なガード（原則8違反）。
7. **本番成果物を種にした fixture**（原則9違反）。
8. 型だけの例外照合・上書き可能な既定値を「契約」と呼ぶテスト・未照合のハッシュ生成（原則10違反）。
9. 継ぎ目（ファイル往復・結合）をメモリ上の突き合わせで代替したテスト・正常系結合ゼロの構成（原則11違反）。

## 付録: 変異スモークの実施手順

「変異スモーク」= 実装を意図的に壊し、テストが赤くなることを確認する抜き取り検査。
（テストのテスト。系統的な全量変異テストではなく、契約に列挙された急所の確認）

1. **変異は構文的に妥当な形で当てる**。行削除で `if` の中身が空になると IndentationError で
   「1 error」になり、pass/fail だけ見ると検出に見える（偽 DETECTED）。
   ガード無効化は行削除ではなく `pass` 置換・条件の `False` 化で行う。
2. **記録は「どのテストが・何のメッセージで落ちたか」まで残す**。
   「N failed」だけでは収集エラーと本物の検出を区別できない。
3. 変異は1件ずつ当て、**確認後に必ず復元**する。次の変異へ進む前に
   `git status --porcelain` がクリーンであることを確認する
   （text モード書き戻しの改行コード変換で dirty になる事故に注意。`newline=""` で読み書き）。
4. 変異の種類は「ガードの無効化」と「**違反入力の投入**」の両方を含める
   （前者だけだと、ガード自体が自己参照で恒真の場合に見逃す）。
