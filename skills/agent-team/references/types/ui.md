# 作業の型: 画面

[1] で、依頼が画面（見た目・文言・配置・操作）を作る・直すものならこの型を使う。ほかの型の作業（リファクタなど）でも、画面に見える部分が変わるならこの型も一緒に読む。中身は UI 規約（プロジェクトにあればそれ、無ければ `~/.agents/docs/ui-policy.md`）にある。この型は、規約の原則12「進め方」を工程に割り当てるだけで、UI の原則は足さない。
この型は、自分の見出しにある段の中身を決める。見出しの無い段は共通本体どおりに進める。

## [2] 調査の問い

- 同じ意味のものを、ほかの画面でどう表しているか（規約の原則5。差分の外の画面も探す）。
- 最悪の条件（最小の幅・最大の件数・最長の文字）で、今の画面はどうなるか（原則2）。

## [3] 契約の既定欄

- 見た目・文言・配置を新しく決めるなら、状態ごと（何も選んでいない・選んでいる・エラーがある・件数が多い）の動くモックを複数作り、計画の承認の材料に入れる。人間が選んだモックを契約の「モック」欄に書き、以後は見た目の判断で人間を待たない。
- 契約の「画面確認」欄を埋める（dispatch「画面確認（前倒し）」）。欄には確かめる操作の一覧を書く（修飾キーを押しながらの操作、フォーカスがボタンにあるときのキー、保存中・読み込み中の戻る・閉じる・キャンセル）。当てはまらない操作も消さず「該当なし: 理由」と書く。
- 足す操作・設定・表示のそれぞれに理由を書く。理由を書けないものは足さない。

## [6] 検証

- 仕上がりを撮影してモックと並べ、違いを確かめる（規約の確かめ方にある状態も、撮れる範囲で撮る）。画像を開いた確認の記録が無いものは合格にしない。

## [8] 報告

モックとの違いと、モックで決まっていなかった見た目を規約のどの原則で決めたかを、完了報告の骨組みの2に入れる。
