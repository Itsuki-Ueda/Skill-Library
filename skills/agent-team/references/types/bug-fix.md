# 作業の型: 不具合修正

[1] で、依頼が不具合（期待と違う動き・エラー・データの誤り）の修正ならこの型を使う。
この型は、自分の見出しにある段の中身を決める。見出しの無い段は共通本体どおりに進める。
主に使う原則: 根本原因を直す（`~/.agents/docs/principles/fix-root-causes.md`）、本物で確かめる、前提を疑う。

## [1] 受付

- 人間の報告から「再現の手順・期待した結果・実際の結果」を1行ずつ書き出す。足りない分は、試して埋められるなら試して埋める（原則「試せば分かることは聞かない」）。
- Acceptance の1行目は「元の再現手順で、期待した結果になる」にする。

## [2] 調査の問い

調査担当に次を渡す。規模が小さく親が自分で確かめられるなら、親が確かめる。

1. 再現できるか。最小の再現条件は何か（入力・状態・環境を1つずつ外して確かめる）。
2. 原因の候補を挙げ、残りを半分に絞れる観察は何か。観察して候補を外し、1つ残るまで続ける。推測で絞らない。状態が見えなければ記録（ログ・print）を足し、動いているときの値を読む。
3. 症状の出た場所ではなく、最初に間違えた場所はどこか。その場所を通る呼び出し元はほかにいくつあるか（同じ共有コードを使うほかの入口でも同じ不具合が出るか）。
4. 回帰なら、いつ、どの変更から壊れたか（git log・git bisect）。
5. 動いている最中にしか見えない不具合（遅い・止まる・メモリが増える）は、推測でなく動いているときの記録（プロファイル・トレース・ログ）を取り、関数と行まで落とす。記録が既にあれば、取り直さずにそれを読む。

- 同じ前提の原因候補が2回外れたら、前提を疑う（`~/.agents/docs/principles/attack-the-premise.md`）。
- 原因の報告は、値が変わった観察と、その行が原因だという因果を分ける（dispatch「検証・雑務」）。

## [3] 契約の既定欄

- Goal に根本原因を1文で書く（どこが、何を間違えているか）。症状の場所しか書けないなら[2]に戻る。
- Allowed paths に原因の場所を入れる。症状の場所だけを手当てする契約にしない。共有コードが原因なら、それを使うほかの呼び出し元での結果も Acceptance に入れる。
- テストの順番: 修正の前に「今のコードで落ちる再現テスト」を書き、今のコードで流して落ちた出力を報告に入れてから修正する。テストと修正は同じ task commit に入る（worker は commit せず、親はレビュー合格後に1回だけ commit するため）。安い局所テストが書けない（重い結合が要る、何を確かめるか曖昧）場合は、Verification に元の再現手順をそのまま書き、テストを省く理由を契約に書く。
- 再現テストを書くなら、変異リストに「修正を元に戻す → 再現テストが落ちる」を必ず入れる。
- 証拠で裏付けられない「念のため」の変更は入れない。仮説が外れたら、その仮説で足した変更を戻す。

## [6] 検証

- 元の再現手順を同じ環境で流し、期待した結果になることを確かめる。「たぶん直った」「別の環境で確かめた」は合格にしない。
- 再現テストを書いたなら、修正前のコードでは落ち（worker の報告の出力）、修正後では通ることを確かめる。省いたなら、元の再現手順を修正前と修正後の両方で流し、結果が期待どおりに変わった出力を記録する。
- [2] で見つけたほかの呼び出し元でも、同じ不具合が出ないことを確かめる。

## [8] 報告

何が壊れていたか、根本原因、どう直したか、どう確かめたかを、完了報告の骨組みの2の行に入れる。
