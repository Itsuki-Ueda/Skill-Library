# dispatch — 割当・並列実行・レビュー

共通本体の[3]〜[6]で読む。起動コマンド・モデル・失敗時の実行経路は使用中のハーネス用ラッパーを参照する。
設定キーは互換性のため維持し、本文では役割を主語にする。

## ルーティング判定

契約作成後にworkerへ残る不確実性と実行先の能力で上から判定する。
1. **環境・探索レーン（既存キー `cc-worker`）**: 既定workerの権限・ツールでは必要な検証や環境構築ができない、または探索しながら担当範囲を確定する必要がある。未確定の範囲は調査で明らかにし、編集前に親が契約を更新する。契約外編集の許可ではない。
2. **難度レーン（`hard-worker`）**: 複数のコードパスの理解、新規で複雑な実装、原因未特定のデバッグ、データ整合性・セキュリティ・共有基盤への変更。
3. **通常レーン（`worker`）**: 確定した局所実装。既存UIパターンに沿う変更も含む。

ファイル数・行数だけで難度を上げない。事前調査で解決済みの複雑さは数えず、残る理解・判断を評価する（E5）。
実行可否はモデル名ではなく実行先の権限とツールに基づく。

## 契約・起動

- `~/.agents/skills/team-worker/SKILL.md` と契約全文を名指しして渡す。他に必要なスキルも明記する。
- Verificationはworkerが実行可能な自己検証。統合ゲートは親の責任であり、workerに不可能な検証を要求しない。
- workerがテストを実行できない環境でテストを書く契約は、「workerが書く → 進行管理者が実行して結果を返す → workerが直す」の往復を計画段階で工程に含める。レビューで初めて実行するのは遅い。
- 対象範囲、除外範囲、成功条件、依存、参照関係、該当時の変異リストを埋める。
- 起動したsession ID・開始時刻・成果物パスをミッションに記録する。読み取り専用担当を含む報告の保存は親が行う。
- 完了通知またはハーネスの待機手段で回収する。ハング疑いはログと生存状態を確認し、同じ呼び出しを無制限に繰り返さない。

## 並列実行の規律

- 設定されたparallel_max以内、Allowed paths非交差、依存解決済みの契約だけ並列実行する。
- **作業ツリーも競合資源に数える。** 各タスクの実行検証（verify.post_change・テスト・変異）が他タスクのAllowed pathsを読み込む場合（全体ビルド・型チェック・エンジン起動を伴うテスト等）、同一ツリーでは実装だけが並列で、検証・commitは全workerの停止待ちになる。この場合は[3]でレーンをworktreeに分ける（作成・後片付けはgit-ops）。分けない判断をするなら、停止待ちの直列化を並列計画に明記する。
- レーンは合流後に統合後HEADで再検証する。実時間に依存するテストは他レーンのプロセスと同時に走ると落ちやすいので、合流後に単独で再実行する。
- 同一ツリーの他タスクの編集を取り消さない。レビュー対象はタスクのパスに絞り、tracked差分だけでなく新規・削除・stage済みファイルも含める。
- 契約外変更は起動前の状態・各タスクの所有範囲と照合して帰属を確認する。他workerの変更を当該workerの違反と誤認しない。
- テスト失敗は自タスク／他タスクWIPを切り分ける。変異確認は対象テスト単体で「変異前green → 変異後red → 復元後green」を確認する。
- 基準greenを作れない場合は延期する。他タスク起因の失敗を変異の検出と数えない。
- 集約ファイル（登録・export・テスト一覧等）は親の担当。worker契約から外し、登録の責任を明記する。親がレビュー前に登録し、登録を含めた合格commitに同梱する。
- 完了ごとにレビューと依存解決を進め、他タスクのバッチ完了を待たない。

## レビューと版記録

- 計画はteam-plan-reviewer、コードはteam-code-reviewerを名指しする。通常ミッションのレビュー担当の組合せはハーネス用ラッパーに従う。expressはexpress.mdに従う。
- 初回は新規の文脈で、契約・元の要求・対象の版・必要な根拠を渡す。作者情報と他レビュアーの結論を先に与えて判断を誘導しない。
- レビュアーは対象と周辺を直接読む。指摘にはP0〜P3、箇所、具体的な壊れ方と根拠を要求する。簡潔さは具体的な保守負担で評価し、好みや指摘数を目的にしない。
- **合格はP0〜P2ゼロ**。複数ゲートがある場合は全ゲートが同じ最終版に対して合格する。指摘は統合し1回で差し戻す。
- `queue/reviews/` の記録は **対象版・対象範囲・担当/ベンダー・判定・指摘・証拠** を含む。
- commit済みなら対象commitと比較元を記録する。未commitなら比較元、tracked差分（stage済みを含む）、新規ファイルのパスと内容を一緒に保存し、そのスナップショットの識別情報を記録する。文書レビューは文書の版または内容ハッシュを記録する。
- レビュー中は対象ファイルを変更しない。変わったら対象版を更新して影響箇所を再レビューする。task commit後もレビュー対象との内容一致を確認する。

## 画面確認（前倒し）

- 画面の見た目・操作がAcceptanceに入るタスクは、契約の「画面確認」欄に確認する画面・状態・操作・撮影条件を書く。修飾キー・キーボード・フォーカスの戻り先・キャンセル時の挙動などの操作は、可能な限り自動テストとしてVerificationに入れる。
- **撮影はworkerが行う。** workerは最後の変更の後に `~/.agents/skills/agent-team/scripts/capture.sh` で契約の画面を撮り（開発サーバの起動・撮影・停止まで1コマンド）、PNGのパスを報告する。保存先は `%TEMP%/agent-team-screens/<リポジトリ名>/<タスクID>/`（Git Bashでは `/tmp/...`）。リポジトリの外に置くのは、Codexのsandboxが作業場所内の `.agents/` への書き込みを拒否し、他の場所ではgit状態を汚すため。
- 進行管理者は、そのタスクのレビュー合格後・task commit前に、workerのPNGを開いて確認する（撮り直さない）。画像を読めるレビュアーには、レビュー依頼に画像パスを含めてよい。全タスクの完了を待たない。自動テストにできない操作だけ、進行管理者が実ブラウザで確認する。
- 確認の所見はレビュー記録に文章で残し、task commitの時点でそのタスクの撮影フォルダ（`%TEMP%/agent-team-screens/<リポジトリ名>/<タスクID>/`）を削除する。画像は保存しない（際限なく溜めない）。差し戻しで撮り直す場合も、確認済みの古い画像は消してから撮る。
- workerが撮れない場合（外部サービスのデータが要る画面、sandbox内で開発サーバが起動しない等）は、workerが「未実行: 理由」を報告し、進行管理者が同じスクリプトで撮る。`capture.sh` はブラウザで開けるWeb画面専用で、デスクトップアプリ（WPF等）の画面は進行管理者が実画面で確認する。`capture.sh` はログイン操作をしないので、認証が要る画面はログイン画面しか撮れない（その画面は進行管理者が実ブラウザで確認する）。
- 親はdispatch前にworktreeを実行可能な状態にする: 依存の取得・復元（`npm ci` / `dotnet restore` 等。CLIのsandboxは外部通信できない）と、git管理外の設定（`.env.local` 等）のコピー。CLI sandboxの既知の制限と対処は `~/.agents/docs/codex-protocol.md` §3e。
- 見た目の不具合はそのタスクの差し戻しとして扱い、他タスクの進行と並行して直す。
- 合流後の最終確認は、統合した画面を通しで軽く見る（タスク間の干渉だけを確認する）。タスク単位の確認はやり直さない。
- 外部サービスのデータが要る画面は、そのサービスへ届く実行場所で確認する（Codexのrestricted sandboxは外部へ通信できない）。

## 再レビュー・上限

- 指摘元には①対処 ②修正が生んだ退行を依頼する。合格済み担当には前回合格版からの**差分と影響範囲**を依頼する。全量再読は既定にしないが、必要な周辺は読む。
- 同じレビュアーを継続する。継続できない経路では前回記録・対象版・新しい差分を新規呼び出しへ渡す。
- 実行・仕様・検証に影響しない表記修正だけ再レビュー省略可。対象変更と省略理由を記録する。旧版の合格を無条件に新版へ流用しない。
- 1ラウンドは「指摘統合 → 修正 → 再レビュー」。上限はlimitsのplan/task/expressを使う。
- ラウンド番号（rN）はレビューの差し戻しだけを数える。worker非実行環境での「書く → 実行 → 直す」の往復やNEED-RUN・NEED-DECISIONの応答は数えず、記録では別の番号（eN等）で区別する。混ぜると上限の遵守を後から確認できない。
- 計画の上限超過は共通本体[3]へ。タスクの上限超過は同じworkerを続投させず、理解不足なら難度レーン、契約の曖昧さなら再分解、環境不足なら環境レーンへ切り替える。
- 同一タスクで2回の実装者切替、設計の穴・仕様変更、利用枠制限は親へ返す。親で解けない判断だけ人間に確認する。

## 調査結果の採用

- team-researcherの規約に従い、file:line・引用・[read]/[grep]/[inferred]・否定形主張の検索記録を要求する。
- 証拠なし主張は採用しない。結論に効く主張、否定形、記憶との矛盾、コメントと実装の区別が効く検索結果は親が裏取りする。確定値を書く前に必要な再計測をする。
- 独立調査は設定上限内で並列化できる。重要領域の重複から矛盾が出たら裏取りする。
  - 計画の前提を左右する重要領域は、分担はそのまま（全領域をrouting.researchで一通り見る）にしたうえで、その領域だけを担当する調査員をrouting.research-overlap（別モデル）で1人足せる。ルートが未定義のハーネスでは使わない。
  - research-overlapの依頼には、値の入口（読込・正規化）から保存先（型・制約）まで追う観点を加える。
  - research-overlapの報告は手がかりとして扱う。そのモデルだけが挙げた主張のうち判断に効くものは、親が裏取りしてから採用する。
  - 試用中（2026-09-23開始）: research-overlapだけが挙げて採用した事実の件数をミッションに記録する。3ミッション連続でゼロなら廃止を人間に提案する。
- 調査の縮退先はラッパーの定義を使う。読み取り専用担当にはファイル保存を要求せず親が保存する。

## 検証・雑務

- 単発の確認は親が実行する。中間出力が長く結論が短い収集・整形・検証だけ、ラッパーの担当へ委譲できる。
- 実行証拠は対象版・作業場所・コマンド・終了コード・**検査した件数**・必要な出力。終了コード0でも検査件数が0や想定より少なければ空振りとして扱う。成功の散文報告や自己申告のexit codeだけでなく、親が元の実行記録を観測できることを確認する。
- 「原因は〜」という特定報告は、値が変わった観測と、その行が書いたという因果を分ける。後者はその行を無効化したprobe・変異・ログのいずれかを証拠にする。親は証拠を見てから人間へ伝え、推測は推測と書く。
- 観測できなければ親が実行するか、未検証として扱う。テストを実行したかと、要件・退行を検出できるかは別に確認する。
- 破壊的操作の判断は雑務へ委譲しない。

## 縮退と完了

- 必須の別ベンダーレビューが利用不可なら、同一ベンダーの独立レビューは補助として実施可能。ただし**通常のdoneにしない**。
- 既存のBlockersに未達を記録し、「回復待ち／例外受入」を人間に確認する。例外受入時だけ未達内容と明示承認をHuman Decisionsと最終報告に残して完了可能。レビューを達成したとは書かない。
- 原因やエラー未確認のまま縮退しない。担当の変更はラッパーの定義と権限に従う。
