# データの形で表す

決まりごとを if 文のあちこちに散らさず、データの形（型・状態の一覧・対応表・境界での変換）で表す。形が決まりと合っていれば、ありえない状態を作れなくなり、分岐が消える。

## なぜ

書くときに形を選ぶのは安い。あとから形を取り戻すのはリファクタになり、先送りされる。

## やり方

- 散らばった真偽値や段階の検査の代わりに、状態の一覧（状態機械）。ばらばらの引数の代わりに、型の付いたまとまり。複数のファイルに広がる分岐の代わりに、対応表。
- 外から来たデータ（API の応答・JSON・CLI の引数・設定ファイル・環境変数・DB の行）は、境界で1回だけ解釈して型の付いた形にする。内側では検査し直さず、その形を信じる。
- 意味の違う値（利用者 ID と注文 ID など）が同じ文字列や数値の型なら、取り違えられないよう別の型にする。
- 形の正本（スキーマ・マイグレーション・定義ファイル）があるなら、そこから導く。並行して手書きしない。
- 業務の決まりは外の仕組みに頼らない純粋な関数に置き、外側は呼ぶだけの薄い層にする。
- 形を無理に作らない。今の形が明快で、局所的で、育ちそうにないなら、平凡なコードのままでよい。分岐・重複した決まり・ありえない状態のどれも減らさない抽象化は疑う。

## 飛ばしたと分かる印

新しい機能が、既存の if/else の列に1本足すだけで入っている。または、別の真偽値と同期させ続けなければならない真偽値が増えた。
