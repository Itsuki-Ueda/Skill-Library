# UI 作成規約（全プロジェクト共通の既定値）

業務アプリの画面を作る・直すときの原則。計画・実装・レビューの全役割が従う。

**優先順位**: プロジェクトに UI 規約（例: `docs/ui-rules.md`）がある場合は**そちらが優先**。この文書はそれが無い場合の既定値。

各項目は「原則 → なぜ → 例 → 確かめ方」の順に書く。
例は過去に人間から直しを受けた実例で、そのまま真似る型ではない。原則に照らして、そのアプリに合う形を考える。

## 1. 利用者の目線を動かさない

- **原則**: 操作や表示内容の変化で、ほかの要素の位置や大きさを変えない。
- **なぜ**: 要素が動くと、目で探し直すことになり、押し間違いも起きる。
- **例**
  - 絞り込むと横に「解除」の文字が出て、プルダウンが左へずれた。→ 解除は部品の中に収める。
  - スイッチを入れると隣に選択欄が現れ、スイッチが動いた。→ 出ていない間も場所を空けておく。
  - 件数が少ないときだけ検索欄を隠していた。→ 件数で形を変えない。
- **確かめ方**: 状態を切り替える前後で画面を撮影し、周りの要素の座標が同じか比べる（例: 絞り込みなし／あり、スイッチ切／入、0 件／上限件数）。

## 2. 最悪の条件で設計する（最小の幅・最大の件数・最長の文字）

- **原則**: 開発中の手頃なデータではなく、想定の上限で崩れないように作る。
- **なぜ**: 広い画面、数件のデータ、短い名前で作ると、本番の狭い画面や多い件数で崩れる。
- **例**
  - 画面を狭めると、表の見出しや罫線が表の外にはみ出した。
  - 入力欄が潰れて、読めなくなった。
  - 横からパネルを出すと、表が縮んで中身がはみ出した。
  - 操作ボタンが画面の外に見切れた。
  - 項目が増えると崩れる並べ方を選んでいた。
  - 入りきらない文字は、省略しつつ全文も読めるようにする。
- **確かめ方**: 最小幅・最大件数・最長の文字で撮影する（例: 想定する最も狭い画面幅、上限件数のデータ、最長の名前を入れた行、横のパネルを開いた状態）。指摘された画面だけでなく、同じ部品を使う全画面を見る。

## 3. 画面の面積は、情報の量と大事さで配る

- **原則**: 広さは、中身が多く、読む必要があるものに回す。中身が短いもの、たまにしか使わないものには場所を取らせない。
- **なぜ**: 広げても意味のない列やボタンが、肝心の情報を狭くする。
- **例**
  - 状態・権限の列が広く、名前の列が狭かった。→ 短い値は固定幅で細くする。
  - 並べ替えの ↑↓ や、決定・取り消しのボタンが列の幅を食っていた。→ ドラッグやキー操作に置き換えて、幅を空けた。
- **確かめ方**: 画面を広げたとき、増えた幅が読みたい情報に回っているかを見る。

## 4. 利用者に手間をかけさせるのは、それで何かを守れるときだけ

- **原則**: 確認・追加のクリック・遠回りは、失うものを防げるときだけ求める。押せそうに見える範囲は、全部押せるようにする。
- **なぜ**: 意味のない確認は手間になり、本当に危ない確認まで読まれなくなる。
- **例**
  - 保存を押した後に、もう一度「保存しますか」と聞いていた。→ やめた。
  - よく使う操作がメニューの奥にあった。→ 1 回で押せる場所に出した。
  - プルダウンや投げ込み欄で、見た目の枠の一部しか押せなかった。→ 枠の全体を押せるようにした。
  - 逆に、入力途中の内容が消える閉じ方には、知らせるようにした。
- **確かめ方**: よく使う操作を 1 通りやって、確認とクリックの 1 つ 1 つが何を守っているか言えるかを見る。

## 5. 同じ意味のものは、どこでも同じにする

- **原則**: 同じ意味を持つ操作・言葉・並び順・見た目は、アプリの中で 1 つにそろえる。
- **なぜ**: 画面ごとに違うと、そのたびに覚え直すことになり、思い込みで誤操作する。
- **例**
  - 2 つのモーダルで、外を押したときの閉じ方が違った。
  - 同じ「権限が無い」状態を、画面ごとに別の言葉で書いていた。
  - ある画面で決めた並び順が、別の画面では効いていなかった。
- **確かめ方**: 1 か所を直したら、同じ意味のものを全画面から探し、そろっているか確かめる。

## 6. 分かりにくさは、説明文ではなく画面の構成で直す

- **原則**: 迷う箇所に説明を書き足す前に、並べ方・部品・流れを変えて、迷う原因そのものをなくす。画面に残す文字は、無いと操作を誤るものだけにする。
- **なぜ**: 説明は読まれない。読まれても、画面の作りが悪いままでは迷う。
- **例**
  - 取り込み画面に注記を 3 つ書いていた。→ どれも要らず、画面の流れを変えるべきだった。人間の言葉は「小手先の説明ではなく、直観的に流れるように迷わない UI に」。
  - 意味の伝わらない記号を置いていた。
  - 色や塗りで示している意味を、文字でも繰り返していた。
  - 小見出しと大見出しで、同じことを 2 回書いていた。
- **確かめ方**: 画面の文字を 1 つずつ消してみる。消しても操作を誤らないものは消す。

## 7. 作業の順に並べ、次の手を今いる場所の近くに置く

- **原則**: 上から読めば作業の順になるように置く。次にやることは、今の手の近くに見せる。
- **なぜ**: 手順が画面の離れた場所に散らばると、見落としや行ったり来たりが起きる。
- **例**
  - 「ひな形をダウンロード」が下、「ファイルをアップロード」が上にあり、ひな形に気づかれなかった。
  - 選択肢が2つある画面は、先にルートを選ばせ、選んだ方だけを見せるようにした。
  - 補足の表のせいで、主要な操作が画面の外に押し出されていた。
- **確かめ方**: 初めての人の目線で、上から順に操作して、目と手が戻る箇所を探す。

## 8. 操作の結果を、確定する前に見えるようにする

- **原則**: 何を変えたか、何が起きるかを、保存する前に画面の上で見せる。
- **なぜ**: 結果が見えない操作は、怖くて使えないか、気づかずに誤る。
- **例**
  - まとめて付け外しした変更が、表に列が無いため見えなかった。→ 増減を表の中に見せた。
  - 未保存の変更の数と内容を、保存バーで見せた。
  - エラーの行だけに絞れるようにし、直した行は勝手に消さないようにした。
- **確かめ方**: 保存の前に画面だけを見て、変更点を把握できるか確かめる。

## 9. 変化は気づけるように、邪魔にならないように見せる

- **原則**: 出る・消える・状態が変わることは、短い動きで伝える。操作が終わったら、余計な強調を残さない。
- **なぜ**: パッと切り替わると、何が起きたか分からず、雑に見える。終わった後に強調が残ると、まだ何か起きていると誤解させる。
- **例**
  - 保存バーが突然現れる → 伸びて出る動きにした。
  - マウスで操作した後も、ボタンにフォーカスの枠が残った。→ キーボードで操作したときだけ出すようにした。
- **確かめ方**: マウスとキーボードの両方で操作し、終わった後の画面を撮る。

## 10. 入力は寛容にして、差分は内部処理・後続画面で補う

- **原則**: 入力は、利用者がすでに持っている形（手元のファイル、表計算からのコピーなど）や、一部だけの形でも受け付ける。足りない分は後から補えるようにする。出力は、次の作業にそのまま使える完成した形で渡す。
- **なぜ**: 形式に合わせる作業を利用者に押し付けると、使われなくなる。
- **例**
  - 列をそろえた完全なファイルでないと読めなかった。→ 一部の列だけでも読み、残りは確かめる画面で設定できるようにした。
  - 人に送る文面を、組み立てずにそのままコピーして送れる形で出す。
- **確かめ方**: 利用者の実際の作業の前後（どこから持ってくるか、どこへ持っていくか）を書き出し、間の手作業を数える。

## 11. 見本と例は、本物と取り違えても害が無いように作る

- **原則**: 例に使う値は、実在の人や物にしない。見本を入れたまま進めても、壊れないか、すぐ分かるようにする。
- **なぜ**: 例の値が実在すると、誤って本物に送ったり登録したりする。見本の扱いが分からないと、利用者は迷う。
- **例**
  - 入力欄の例に、実在しうるメールアドレスを使っていた。
  - ひな形の見本の行を消すべきかどうかで、迷わせていた。
- **確かめ方**: 例と見本の値を全部挙げ、実在しないか、残したまま進めたら何が起きるかを確かめる。

## 12. 進め方

- **原則**: 見た目・文言・配置は人間が決める。人間が比べて選べる材料を出す。人間が選ぶのは**計画の段階だけ**にする。
- **やり方**
  - 計画の段階で、動くモック（HTML）や文面の案を複数出す。モックは状態ごと（何も選んでいない・選んでいる・エラーがある・件数が多い）に作る。推奨案を示しても、決めるのは人間。選ばれた案は計画の承認と一緒に確定する。
  - 実装に入った後は、選ばれたモックを見た目の正本にして進める。見た目の判断で人間を待たない。モックで決まっていない見た目は、この規約の原則に照らして実装側が決め、報告に書く。
  - 仕上がりは撮影し、モックと見比べて、違いを報告する。
